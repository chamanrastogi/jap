MySQL Basics

Core concepts â€” database, table, schema, and fundamental SQL operations.

MySQL is an open-source relational database management system (RDBMS) that uses Structured Query Language (SQL). It stores data in tables with rows and columns, supports ACID transactions, and is widely used for web applications (LAMP stack). Originally developed by MySQL AB, now owned by Oracle Corporation.

In MySQL, database and schema are synonymous â€” CREATE DATABASE and CREATE SCHEMA do the same thing. However, in other RDBMS like PostgreSQL, a schema is a namespace within a database (tables, views, etc.), while a database is a container of schemas.

MySQL default port is 3306 (TCP). For MySQL X Protocol (used by X DevAPI), the default port is 33060. 

CREATE DATABASE mydatabase;
CREATE DATABASE IF NOT EXISTS mydatabase
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

-- Switch to the database
USE mydatabase;

CREATE TABLE users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  age INT DEFAULT 0,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

  • CHAR(n) â€” Fixed-length. Always stores exactly n characters, padding with spaces. Max 255 characters. Faster for fixed-length data like country codes, ZIP codes.
  • VARCHAR(n) â€” Variable-length. Stores up to n characters, using 1â€“2 extra bytes for length prefix. Max 65,535 characters (subject to row size). Saves space for variable-length data like names, emails.

Major storage engines:
  • InnoDB (default) â€” ACID-compliant, transactions, foreign keys, row-level locking
  • MyISAM â€” No transactions, table-level locking, full-text search (older), faster for reads
  • Memory (HEAP) â€” In-memory data, volatile, extremely fast
  • CSV â€” Stores data as CSV files
  • Archive â€” Compressed storage, insert-only, no indexing
  • NDB Cluster â€” Distributed, high-availability clustering

A Primary Key is a column (or set of columns) that uniquely identifies each row in a table. It must contain unique values and cannot be NULL. Each table can have only one primary key. MySQL automatically creates a clustered index on the primary key (InnoDB).

A Foreign Key is a column (or set of columns) that establishes a link between data in two tables. It references the primary key of another table, enforcing referential integrity. Foreign keys are only supported by InnoDB. 
CREATE TABLE orders (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT,
  FOREIGN KEY (user_id) REFERENCES users(id)
    ON DELETE CASCADE
);

  • DDL (Data Definition Language) â€” CREATE, ALTER, DROP, TRUNCATE, RENAME
  • DML (Data Manipulation Language) â€” SELECT, INSERT, UPDATE, DELETE
  • DCL (Data Control Language) â€” GRANT, REVOKE
  • TCL (Transaction Control Language) â€” COMMIT, ROLLBACK, SAVEPOINT

NULL means "unknown" or "no value." It is not the same as an empty string '' or zero 0. Use IS NULL / IS NOT NULL to check. Any arithmetic operation with NULL yields NULL. COUNT(column) excludes NULLs, but COUNT(*) includes all rows.

Both combine result sets from multiple SELECT queries. Both require the same number of columns and compatible data types.
  • UNION â€” Removes duplicate rows (performs a sort/distinct). Slower.
  • UNION ALL â€” Keeps all rows including duplicates. Faster.

AUTO_INCREMENT generates a unique numeric value automatically for each new row. It starts at 1 (by default) and increments by 1. Used primarily for surrogate primary keys. You can retrieve the last generated value using LAST_INSERT_ID().

Window functions perform calculations across a set of rows related to the current row without collapsing them into a single output row (unlike GROUP BY). MySQL 8+ supports them. 
SELECT
  name, department, salary,
  ROW_NUMBER() OVER (ORDER BY salary DESC)              AS `rank`,
  RANK()       OVER (ORDER BY salary DESC)              AS `rank_with_gaps`,
  DENSE_RANK() OVER (ORDER BY salary DESC)              AS `dense_rank`,
  NTILE(4)     OVER (ORDER BY salary DESC)              AS `quartile`,
  LAG(salary)  OVER (ORDER BY salary)                   AS `prev_salary`,
  LEAD(salary) OVER (ORDER BY salary)                   AS `next_salary`,
  SUM(salary)  OVER (PARTITION BY department)             AS `dept_total`,
  AVG(salary)  OVER (PARTITION BY department)             AS `dept_avg`,
  FIRST_VALUE(name) OVER (PARTITION BY department
                        ORDER BY salary DESC)       AS `highest_paid`
FROM employees;

A correlated subquery is a subquery that references columns from the outer query. It is re-evaluated for every row processed by the outer query, which can make it slow on large datasets. 
-- Find employees earning more than department average
SELECT e1.name, e1.salary, e1.department
FROM employees e1
WHERE e1.salary > (
  SELECT AVG(e2.salary)
  FROM employees e2
  WHERE e2.department = e1.department
);

A CTE (introduced in MySQL 8.0) is a temporary named result set that exists only within a single query's scope. It improves readability and allows recursion. 
WITH high_earners AS (
  SELECT id, name, salary
  FROM employees
  WHERE salary > 100000
)
SELECT * FROM high_earners
WHERE id IN (SELECT user_id FROM orders);

-- Recursive CTE (hierarchy)
WITH RECURSIVE org_tree AS (
  SELECT id, name, manager_id, 1 AS level
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, t.level + 1
  FROM employees e
  JOIN org_tree t ON e.manager_id = t.id
)
SELECT * FROM org_tree;

SELECT * FROM users ORDER BY id LIMIT 10;

DISTINCT removes duplicate rows from the result. GROUP BY groups rows that have the same values and is typically used with aggregate functions. When used without aggregates, GROUP BY behaves like DISTINCT but sorts the result (which can be avoided with ORDER BY NULL). GROUP BY is more flexible as it allows aggregations.

MySQL does not have a built-in PIVOT operator. Use conditional aggregation with CASE: 
SELECT

  SUM(CASE WHEN gender = 'Male' THEN 1 ELSE 0 END) AS male_count,
  SUM(CASE WHEN gender = 'Female' THEN 1 ELSE 0 END) AS female_count
FROM employees
GROUP BY department;

Joins & Subqueries

Understanding table relationships with JOINs and subqueries.

JOIN combines rows from two or more tables based on a related column. Types:
  • INNER JOIN â€” Returns rows that have matching values in both tables
  • LEFT JOIN (or LEFT OUTER JOIN) â€” Returns all rows from left table + matched rows from right table
  • RIGHT JOIN â€” Returns all rows from right table + matched rows from left table
  • CROSS JOIN â€” Cartesian product of both tables
  • NATURAL JOIN â€” Joins on columns with the same name (not recommended for clarity)
  • SELF JOIN â€” Joining a table with itself

SELECT
  u.id, u.name,
  COALESCE(COUNT(o.id), 0) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name
ORDER BY order_count DESC;

Given students (id, name) and enrollments (student_id, course): 
-- INNER: only students who enrolled
SELECT s.name, e.course
FROM students s
INNER JOIN enrollments e ON s.id = e.student_id;

-- LEFT: all students, even those without enrollments
SELECT s.name, e.course
FROM students s
LEFT JOIN enrollments e ON s.id = e.student_id;

A SELF JOIN is a regular join where a table is joined with itself. Use table aliases to distinguish. 
-- Employee-manager relationship
SELECT
  e1.name AS employee,
  e2.name AS manager
FROM employees e1
LEFT JOIN employees e2 ON e1.manager_id = e2.id;

ON specifies any join condition (columns need not have the same name). USING is shorthand when the join columns have the same name in both tables. USING eliminates the duplicate column from the result. 
-- ON
SELECT * FROM users u
JOIN orders o ON u.id = o.user_id;

-- USING (same column name in both tables)
SELECT * FROM users
JOIN profiles USING (user_id);

A CROSS JOIN produces the Cartesian product of two tables â€” every row from table A paired with every row from table B. No join condition is specified. 
SELECT colors.name, sizes.name
FROM colors
CROSS JOIN sizes;

-- Same as implicit CROSS JOIN
SELECT colors.name, sizes.name
FROM colors, sizes;
Be careful: CROSS JOIN on large tables can generate enormous result sets.

  • JOIN â€” MySQL optimizer can leverage indexes more effectively. Generally faster for correlated data.
  • Subquery â€” Easier to read and maintain. Modern MySQL (8.0+) has better subquery optimization (auto-transform many subqueries to joins).
Best practice: Prefer JOINs for large datasets. Use subqueries for readability when the dataset is small or when you need intermediate aggregations. 

-- Using LEFT JOIN
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;

-- Using NOT EXISTS
SELECT u.id, u.name
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- Using NOT IN (caution with NULLs)
SELECT u.id, u.name
FROM users u
WHERE u.id NOT IN (
  SELECT user_id FROM orders WHERE user_id IS NOT NULL
);

Indexing

Types of indexes, query optimization, EXPLAIN, and best practices.

An index is a data structure (like a B-Tree) that improves the speed of data retrieval operations on a table at the cost of additional storage and slower writes (INSERT/UPDATE/DELETE). Indexes are created on one or more columns and help the database find rows without scanning the entire table.

  • B-Tree Index â€” Default for InnoDB/MyISAM
  • UNIQUE Index â€” Ensures all values are unique
  • PRIMARY KEY â€” Unique + NOT NULL; clustered index in InnoDB
  • FULLTEXT Index â€” For full-text search (MATCH ... AGAINST)
  • SPATIAL Index â€” For geographic data types (POINT, POLYGON)
  • Hash Index â€” Only in Memory engine
  • Composite Index â€” Multi-column index, leftmost prefix rule applies
  • Descending Index â€” MySQL 8.0+
  • Functional Index â€” MySQL 8.0.13+ â€” index on expressions

A composite index is an index on multiple columns. Example: INDEX idx_name_age (name, age).

Leftmost Prefix Rule: A composite index can be used for queries on any leftmost subset of its columns. An index on (A, B, C) can optimize:
  • WHERE A = ? â€” uses index
  • WHERE A = ? AND B = ? â€” uses index
  • WHERE A = ? AND B = ? AND C = ? â€” uses index fully
  • WHERE B = ? â€” cannot use the index (skips column A)
  • WHERE A = ? AND C = ? â€” uses index for A but not for C (gap)

-- Create index
CREATE INDEX idx_name ON users (name);
CREATE UNIQUE INDEX idx_email ON users (email);
CREATE INDEX idx_name_age ON users (name, age);

-- Add via ALTER TABLE
ALTER TABLE users ADD INDEX idx_name (name);

-- Drop index
DROP INDEX idx_name ON users;

-- Show indexes
SHOW INDEX FROM users;

EXPLAIN shows how MySQL executes a query. 
EXPLAIN SELECT u.name, COUNT(o.id)
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.age > 18
GROUP BY u.id;
Key columns in EXPLAIN output:
  • type â€” ALL (bad), range, ref, eq_ref, const (best)
  • possible_keys â€” Indexes MySQL could use
  • key â€” Index MySQL actually used
  • rows â€” Estimated rows examined
  • Extra â€” Using index (covering), Using filesort (bad), Using temporary (bad)
Use EXPLAIN ANALYZE (MySQL 8.0.18+) for actual execution times.

A covering index is an index that contains all columns needed by a query, so MySQL can satisfy the query entirely from the index without accessing the table rows. Indicated by Using index in EXPLAIN Extra column. 
-- If index is on (name, age), this query is covered:
SELECT name, age FROM users WHERE name = 'Alice';

Clustered Index: InnoDB stores the actual table data in a B-Tree structure ordered by the primary key. The table data is the clustered index. There can be only one per table. Secondary indexes store the primary key value as a pointer.

Non-Clustered Index: The index structure is separate from the data. The index leaf nodes contain pointers to the actual rows. MyISAM uses non-clustered indexes. In InnoDB, all secondary indexes are non-clustered.

  • Write-heavy tables â€” Each INSERT/UPDATE/DELETE must update all indexes
  • Small tables â€” Full table scan is faster than index traversal
  • Low cardinality columns â€” e.g., gender column (M/F)
  • Too many indexes â€” Increased storage and slower writes
  • Columns frequently updated â€” Index maintenance overhead
  • Queries with LIKE '%text%' â€” Wildcard at start prevents B-Tree usage

Index Merge is an optimization where MySQL uses multiple indexes in a single query and merges the results. It can merge using AND (intersection), OR (union), or a combination. Appears in EXPLAIN as Using union(index_a,index_b). Index merge is typically slower than a well-designed composite index because it involves reading multiple B-Trees and sorting/merging results.

Normalization

Database normalization forms, denormalization, and schema design principles.

Normalization is the process of organizing data to reduce redundancy and improve data integrity. It involves dividing large tables into smaller, related tables and defining relationships between them.

  • 1NF â€” Each column contains atomic values. No repeating groups. Each row must be unique.
  • 2NF â€” Must be in 1NF. Every non-key column must be fully functionally dependent on the entire primary key (no partial dependency). Relevant for composite keys.
  • 3NF â€” Must be in 2NF. No transitive dependency â€” non-key columns should not depend on other non-key columns.
  • BCNF â€” Stricter version of 3NF. Every determinant must be a candidate key.
Example violation: Table Employee(emp_id, dept_id, dept_location) â€” dept_location depends on dept_id, not emp_id (3NF violation). Solution: separate Department table.

Denormalization is the intentional introduction of redundancy by combining tables or adding duplicate columns. It trades write efficiency and storage for read performance.

When to denormalize:
  • Reporting/analytics queries that need to avoid expensive JOINs
  • High-traffic read-heavy applications (e.g., dashboards)
  • Caching pre-computed aggregates
  • Read-heavy OLAP workloads

An ER Diagram is a visual representation of entities (tables), their attributes (columns), and the relationships between them (one-to-one, one-to-many, many-to-many). It is used for database design to plan the schema before implementation.

Use a junction (pivot) table that contains foreign keys referencing both related tables. 
CREATE TABLE enrollments (
  student_id INT,
  course_id INT,
  enrolled_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES students(id),
  FOREIGN KEY (course_id) REFERENCES courses(id)
);

Constraints

NOT NULL, UNIQUE, CHECK, DEFAULT, FOREIGN KEY constraints.

  • NOT NULL â€” Column cannot contain NULL values
  • UNIQUE â€” All values in the column must be distinct
  • PRIMARY KEY â€” NOT NULL + UNIQUE (one per table)
  • FOREIGN KEY â€” Enforces referential integrity (InnoDB only)
  • CHECK â€” Validates values based on an expression (MySQL 8.0.16+ enforced)
  • DEFAULT â€” Provides a default value when none is specified

CHECK constraint limits values using a boolean expression. MySQL 8.0.16+ enforces them. 
CREATE TABLE employees (
  id INT PRIMARY KEY,
  age INT CHECK (age >= 18 AND age <= 100),
  salary DECIMAL(10,2) CHECK (salary > 0),
  status VARCHAR(10) CHECK (status IN ('active','inactive','terminated'))
);

  • ON DELETE CASCADE â€” When a parent row is deleted, all child rows are automatically deleted.
  • ON DELETE SET NULL â€” When a parent row is deleted, the FK column in child rows is set to NULL.
  • ON DELETE RESTRICT â€” Prevents deletion of parent row if child rows exist (default).
  • ON DELETE NO ACTION â€” Same as RESTRICT in MySQL.

A cursor allows you to iterate through a result set row by row inside a stored procedure. Cursors are memory-intensive and should be used as a last resort. 
CREATE PROCEDURE process_users()
BEGIN
  DECLARE done INT DEFAULT FALSE;
  DECLARE uid INT;
  DECLARE uname VARCHAR(100);
  DECLARE cur CURSOR FOR
    SELECT id, name FROM users WHERE status = 'pending';
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = TRUE;
  OPEN cur;
  read_loop: LOOP
    FETCH cur INTO uid, uname;
    IF done THEN LEAVE read_loop; END IF;
    UPDATE users SET status = 'processed' WHERE id = uid;
  END LOOP;
  CLOSE cur;
END;

Triggers & Events

Automated actions on data changes and scheduled events.

A trigger is a stored program that automatically executes in response to INSERT, UPDATE, or DELETE on a table. It can fire BEFORE or AFTER the event. Use triggers for auditing, validation, or derived data. 

CREATE TABLE user_deletion_log (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT, name VARCHAR(100),
  email VARCHAR(255),
  deleted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

DELIMITER $$
CREATE TRIGGER before_user_delete
BEFORE DELETE ON users
FOR EACH ROW
BEGIN
  INSERT INTO user_deletion_log (user_id, name, email)
  VALUES (OLD.id, OLD.name, OLD.email);
END $$
DELIMITER ;

  • BEFORE â€” Fires before the operation. Can modify values before writing. Can raise errors to prevent the operation.
  • AFTER â€” Fires after the operation. Cannot modify the data. Useful for logging, audit trails, cascading actions.

An Event is a scheduled task that runs at specified intervals (like cron inside MySQL). 
SET GLOBAL event_scheduler = ON;

CREATE EVENT daily_cleanup
ON SCHEDULE EVERY 1 DAY
STARTS '2025-01-01 00:00:00'
DO
  DELETE FROM sessions WHERE expires_at < NOW();

SHOW EVENTS;

  • Cannot use ALTER, DROP, CREATE inside triggers
  • Cannot return result sets
  • Cannot commit or rollback transactions
  • Hard to debug
  • Can degrade performance for bulk operations

Transactions & Locking

ACID, isolation levels, locks, deadlocks, and MVCC in InnoDB.

A transaction is a sequence of SQL operations executed as a single unit of work. It follows ACID properties. Only InnoDB supports transactions. 
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- or ROLLBACK; if error

  • A â€” Atomicity: All operations succeed or all fail (rollback).
  • C â€” Consistency: Transaction moves DB from one valid state to another.
  • I â€” Isolation: Concurrent transactions are isolated from each other.
  • D â€” Durability: Committed changes persist even after system failure (via redo logs).

Isolation LevelDirty ReadNon-Repeatable ReadPhantom Read
READ UNCOMMITTEDPossiblePossiblePossible
READ COMMITTEDPreventedPossiblePossible
REPEATABLE READPreventedPreventedPrevented (via gap locks)
SERIALIZABLEPreventedPreventedPrevented
MySQL default is REPEATABLE READ. 
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

  • Dirty Read â€” Transaction A reads uncommitted data from B. If B rolls back, A read invalid data. Prevented by READ COMMITTED+.
  • Non-Repeatable Read â€” Transaction A reads same row twice with different values because B committed an update in between. Prevented by REPEATABLE READ+.
  • Phantom Read â€” Transaction A runs same query twice and sees different rows because B inserted rows. InnoDB prevents phantoms at REPEATABLE READ using next-key locks.

InnoDB uses various locking mechanisms:
  • Row-level locks (record locks) â€” Lock individual index records
  • Gap locks â€” Lock gaps between index records to prevent phantom inserts
  • Next-key locks â€” Record lock + gap lock combination
  • Shared (S) locks â€” Allow reading, block writing (SELECT ... LOCK IN SHARE MODE)
  • Exclusive (X) locks â€” Block both reading and writing (SELECT ... FOR UPDATE)
  • Intention locks â€” Table-level locks indicating intent to acquire row-level locks
  • AUTO-INC locks â€” For auto-increment column insertion

A deadlock occurs when two or more transactions each hold locks that the other needs, creating a cycle. InnoDB automatically detects deadlocks and rolls back one transaction (the "victim").

Prevention tips:
  • Access tables and rows in the same order across transactions
  • Keep transactions short
  • Use proper index (reduces lock contention)
  • Use READ COMMITTED to reduce gap locking
  • Consider using SELECT ... FOR UPDATE NOWAIT or SKIP LOCKED
Check deadlocks: SHOW ENGINE INNODB STATUS;

MVCC (Multi-Version Concurrency Control) is a mechanism used by InnoDB to allow multiple transactions to see a consistent snapshot of data without blocking each other. It works by keeping multiple versions of each row (with transaction IDs and rollback pointers). Readers do not block writers, and writers do not block readers (at REPEATABLE READ and READ COMMITTED). Each transaction sees a snapshot of the data as of when the transaction started (for REPEATABLE READ).

A SAVEPOINT allows partial rollback within a transaction. 
START TRANSACTION;
UPDATE accounts SET balance = 100 WHERE id = 1;
SAVEPOINT sp1;
UPDATE accounts SET balance = 200 WHERE id = 2;
ROLLBACK TO sp1;  -- reverses second update
COMMIT;           -- commits first update

Performance & Optimization

Query optimization, configuration tuning, profiling, and best practices.

Enable the slow query log: 
-- In my.cnf / my.ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 2  -- seconds

-- Or at runtime
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 2;

-- View slow queries
SHOW VARIABLES LIKE 'slow_query_log';
SHOW STATUS LIKE 'Slow_queries';
Also use EXPLAIN and EXPLAIN ANALYZE for individual queries.

The query cache stored the result set of a SELECT query so that repeated identical queries could return instantly. It was removed in MySQL 8.0 because it caused scalability issues (global mutex contention on multi-core systems). Use application-level caching (Redis, Memcached) or MySQL 8.0's performance schema instead.

Steps for optimizing a slow query:
  1. Use EXPLAIN to see execution plan
  2. Check for ALL (full table scan) in type column
  3. Check for Using filesort or Using temporary in Extra
  4. Add appropriate indexes (check if existing indexes are being used)
  5. Avoid SELECT * â€” fetch only needed columns
  6. Ensure JOIN columns are indexed
  7. Break complex queries into simpler steps with temp tables
  8. Use EXISTS instead of IN for subqueries
  9. Consider query rewriting (e.g., avoid functions on indexed columns)
  10. Partition large tables if needed

The query optimizer determines the most efficient way to execute a query. It evaluates multiple strategies (join orders, index choices, access methods) and selects the lowest-cost plan based on statistics. Use EXPLAIN to see the optimizer's plan. You can force index usage with FORCE INDEX or USE INDEX hints. MySQL 8.0 also supports OPTIMIZER_HINTS for fine-grained control.

The Performance Schema (available since MySQL 5.5, enabled by default in MySQL 8.0) provides low-level instrumentation for monitoring query execution, waits, mutexes, file I/O, and memory usage. It can help identify bottlenecks without external tools. 
-- Check if enabled
SHOW VARIABLES LIKE 'performance_schema';

-- Find slow queries from performance_schema
SELECT DIGEST_TEXT, ROUND(SUM_TIMER_WAIT/1000000000, 2) AS total_ms,
       COUNT_STAR, ROUND(AVG_TIMER_WAIT/1000000000, 2) AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

Partitioning divides a table into smaller, more manageable pieces while still querying as a single table. Types: RANGE, LIST, HASH, KEY, COLUMNS. Benefits: faster pruning (partition elimination), easier archival, improved query performance for large tables. 
CREATE TABLE logs (
  id INT NOT NULL,
  created_at DATE NOT NULL,
  message TEXT
)
PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p_old VALUES LESS THAN (2020),
  PARTITION p_2020 VALUES LESS THAN (2021),
  PARTITION p_2021 VALUES LESS THAN (2022),
  PARTITION p_future VALUES LESS THAN MAXVALUE
);

Vertical partitioning splits a table by columns (e.g., moving infrequently used columns to a separate table). Horizontal partitioning splits a table by rows (e.g., by date range). MySQL's PARTITION BY is horizontal partitioning. Vertical partitioning is done manually by splitting the table schema.

Replication & Backup

MySQL replication types, setup, monitoring, and backup strategies.

Replication is the process of copying data from one MySQL server (master/primary) to one or more servers (slaves/replicas). It is used for read scaling, high availability, disaster recovery, and analytics offloading.

  • Asynchronous â€” Master does not wait for slave. Default. Fast but risk of data loss.
  • Semisynchronous â€” Master waits for at least one slave to acknowledge receipt. Balance of speed and safety.
  • Group Replication â€” Multi-primary or single-primary with automatic failover (MySQL 5.7+). Uses Paxos-like consensus.
  • GTID-based â€” Uses Global Transaction Identifiers for easier failover and management.

  • Statement-based (SBR) â€” Logs actual SQL statements. Compact logs. Can break with non-deterministic functions (NOW(), UUID()).
  • Row-based (RBR) â€” Logs individual row changes. More data but safer. Default in MySQL 8.0 for DML.
  • Mixed (MBR) â€” MySQL chooses automatically (statement where safe, row where not). Default in some versions.
SHOW VARIABLES LIKE 'binlog_format';

On Master (my.cnf): 
[mysqld]
server-id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW
On Slave (my.cnf): 
[mysqld]
server-id = 2
relay_log = /var/log/mysql/mysql-relay-bin.log
Commands: 
-- Master: Create replication user
CREATE USER 'repl'@'%' IDENTIFIED BY 'password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- Slave: Configure replication
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = 'master_ip',
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'password',
  SOURCE_LOG_FILE = 'mysql-bin.000001',
  SOURCE_LOG_POS = 0;

START REPLICA;
SHOW REPLICA STATUS;

  • Use stored procedures with parameters
