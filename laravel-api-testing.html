Laravel Testing & API Development

Advanced unit testing and API design with real-life problems Laravel 10+ PHP 8.2+ Pest / PHPUnit

Theory is easy — the real problems appear when you test a payment webhook, mock a slow third-party API, or keep a suite green while 40 tests run in parallel. This guide teaches unit & feature testing and advanced API development by walking through real bugs and production scenarios with complete code examples.

Test Setup Done Right

A flaky suite starts with a misconfigured environment. Get these three files right first.

1. phpunit.xml — isolated test database

<!-- phpunit.xml -->
<php>
    <env name="APP_ENV" value="testing"/>
    <env name="DB_CONNECTION" value="sqlite"/>
    <env name="DB_DATABASE" value=":memory:"/>
    <env name="QUEUE_CONNECTION" value="sync"/>
    <env name="CACHE_STORE" value="array"/>
    <env name="SESSION_DRIVER" value="array"/>
    <env name="MAIL_MAILER" value="array"/>
    </php>
Why: an in-memory SQLite DB keeps tests instant and hermetic. QUEUE_CONNECTION=sync runs queued jobs inline so assertions on side-effects work. Note: SQLite is per-process — see the Parallel Tests section for MySQL/Postgres.

2. RefreshDatabase vs DatabaseTransactions

use Illuminate\Foundation\Testing\RefreshDatabase;
use Illuminate\Foundation\Testing\DatabaseTransactions;

// RefreshDatabase: migrates fresh + rolls back each test (slowest, safest)
final class OrderTest extends TestCase
{
    use RefreshDatabase;
}

// DatabaseTransactions: wraps each test in a transaction (faster,
//   but schema changes and some raw SQL become invisible to tests)
final class PricingServiceTest extends TestCase
{
    use DatabaseTransactions;
}
Rule of thumb: use RefreshDatabase for feature tests touching many tables; use DatabaseTransactions for service/unit-style tests where speed matters and you only insert rows inside a transaction.

3. Model::preventLazyLoading() in tests

// App\Providers\AppServiceProvider::boot()
public function boot(): void
{
    if ($this->app->isProduction()) {
        Model::preventLazyLoading(false);
    } else {
        Model::preventLazyLoading(true);
        Model::preventSilentlyDiscardingAttributes(true);
    }
}
This single line turns every accidental lazy load into a test failure in local/dev/test environments — catching N+1 queries before they hit production.

Unit vs Feature — Which One, When?

Unit Test
  • Tests one class in isolation
  • No HTTP, no database, no real jobs
  • Fakes/mocks collaborators
  • Blazing fast, pinpoints bugs
final class MoneyTest extends TestCase
{
    public function test_applies_percentage_discount(): void
    {
        $money = new Money(10000);

        $discounted = $money->applyDiscount(10);

        $this->assertSame(9000, $discounted->amount);
    }
}
Feature Test
  • Drives the HTTP layer end-to-end
  • Boots the full framework + database
  • Verifies routing, auth, validation, JSON shape
  • Slowest, but protects the user contract
public function test_guest_cannot_create_order(): void
{
    $response = $this->postJson('/api/orders', ['items' => []]);

    $response->assertUnauthorized();
}
Real-life rule: your suite should be ~70% unit (service, value-object, job logic) and ~30% feature (happy path, auth, validation, JSON contract). If a bug is in a controller decision, write a feature test; if it is in a calculation, write a unit test.

Factories & Fakes That Don't Rot

States are the contract of your domain

// database/factories/OrderFactory.php
final class OrderFactory extends Factory
{
    public function definition(): array
    {
        return [
            'number'    => str(fake()->unique()->numberBetween(1000, 9999))->prepend('ORD-'),
            'status'    => OrderStatus::Pending,
            'total_cents' => 0,
            'user_id'   => User::factory(),
            'placed_at' => now(),
        ];
    }

    public function paid(): static
    {
        return $this->state(fn (array $a) => ['status' => OrderStatus::Paid]);
    }

    public function refunded(): static
    {
        return $this->state(fn (array $a) => ['status' => OrderStatus::Refunded]);
    }

    // Relations are part of the contract too
    public function withItems(int $count = 2): static
    {
        return $this->has(OrderItem::factory()->count($count));
    }
}

// Usage everywhere in tests
$order = Order::factory()->paid()->withItems(3)->create();
Problem you will hit: factories that call Http, hit the clock, or reference removed columns. Keep factories pure data — never trigger side effects in definition(). If a factory must run post-creation logic, use afterCreating() so it can be disabled in unit tests.

Fake, don't mock

use Illuminate\Support\Facades\Storage;
use Illuminate\Support\Facades\Queue;
use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Mail;
use Illuminate\Support\Facades\Notification;

Storage::fake('public');
Queue::fake();
Http::fake();
Mail::fake();
Notification::fake();
Laravel's facades ship built-in spies. Using a fake is almost always better than hand-rolled mocks — less setup, real behavior, and chainable assertions like Queue::assertPushed(...).

Real Problem #1: N+1 Queries in an API

The bug: GET /api/orders returns 50 orders. The JSON includes user.name and items, but the controller forgot ->with(...). Production runs 1 + N + M queries — the API is slow, and only an occasional test that counts queries catches it.

The failing controller

public function index(Request $request): OrderCollection
{
    // BUG: no eager loading - each order triggers user + items queries
    $orders = Order::latest()->paginate(50);

    return new OrderCollection($orders);
}

The test that catches it

public function test_index_does_not_lazy_load(): void
{
    $user  = User::factory()->create();
    $orders = Order::factory()->count(10)
        ->for($user)->has(OrderItem::factory()->count(3))
        ->create();

    DB::enableQueryLog();

    $response = $this->actingAs($user)->getJson('/api/orders');

    $response->assertOk();

    DB::assertNoLazyLoaded();   // FAILS on the buggy controller
    DB::assertQueryCount(count(DB::getQueryLog()) < 10);
}
The fix: Order::with(['user', 'items'])->latest()->paginate(50). Turn the guard on globally with Model::preventLazyLoading() (see Setup) so a regression fails in every test, not just the one that counts queries.

Real Problem #2: Time-Sensitive Tests

The bug: a coupon API validates expires_at > now(). The suite passes at 9:00 AM and fails at midnight — or passes today and fails tomorrow because a test creates an order yesterday and asserts on today. Your tests depend on the wall clock.

Freeze time deterministically

use Carbon\Carbon;

public function test_expired_coupon_is_rejected(): void
{
    // Travel to a fixed moment - Carbon::setTestNow() or Laravel's helper
    $this->travelTo(Carbon::parse('2026-01-15 12:00:00'));

    $coupon = Coupon::factory()->create([
        'expires_at' => Carbon::parse('2026-01-14 23:59:59'),
    ]);

    $response = $this->postJson('/api/orders', $this->payload($coupon));

    $response->assertStatus(422)
        ->assertJsonValidationErrors(['coupon_code']);
}

// Related helpers
$this->travel(5)->hours();          // advance 5 hours
$this->travelBack();               // restore real clock
Carbon::setTestNow(null);          // also restores
Rule: every test that touches now(), created_at, or "x hours ago" must call travelTo() first. Never assert on live time.

Real Problem #3: External HTTP APIs

The bug: your payment gateway webhook / geocoding service is down during the CI run. A real Http::client call makes tests flaky, slow, and charges real money. You need deterministic responses.

Http::fake() with URL patterns and sequences

use Illuminate\Support\Facades\Http;

public function test_charge_succeeds_on_gateway_ok(): void
{
    Http::fake([
        'api.paymentgateway.com/*' => Http::response([
            'status' => 'succeeded',
            'id'    => 'ch_123',
        ], 200),
    ]);

    $result = $this->paymentService->charge(5000);

    $this->assertTrue($result);

    // Assert the exact request that went out
    Http::assertSent(function (Request $request): bool {
        return str_contains($request->url(), 'api.paymentgateway.com')
            && $request->hasHeader('Authorization')
            && $request['amount'] === 5000;
    });
}

// Retry scenarios with Http::sequence()
public function test_retries_then_succeeds(): void
{
    Http::fake([
        'api.paymentgateway.com/*' => Http::sequence()
            ->push('Server Error', 500)
            ->push(['status' => 'succeeded'], 200),
    ]);

    $result = $this->paymentService->charge(5000);

    $this->assertTrue($result);
}
Also critical: fake first, then call code that fires requests. Un-faked URLs throw in tests, so you get instant feedback if a request pattern changed. Always assert on Http::assertSent(...) so you test what you send, not just that you survived.

Webhook signature verification test

public function test_rejects_webhook_with_bad_signature(): void
{
    $payload = ['event' => 'payment.failed', 'data' => ['id' => 'ch_123']];

    $response = $this->postJson('/api/webhooks/payment', $payload, [
        'X-Signature' => 'forged-signature',
    ]);

    $response->assertForbidden();
}

Real Problem #4: Queues, Mail & Notifications

The bug: ordering flow dispatches SendOrderConfirmation and sends a Slack notification. Tests with a real queue run jobs whenever (or never), making assertions flaky. Tests also fail when an email is unexpectedly sent in CI.

Queue::fake() + assertPushed

use Illuminate\Support\Facades\Queue;

public function test_placing_order_dispatches_confirmation(): void
{
    Queue::fake([SendOrderConfirmation::class]);

    $user  = User::factory()->create();
    $order = $this->createOrder($user);

    Queue::assertPushed(SendOrderConfirmation::class, function ($job) use ($order): bool {
        return $job->order->is($order);
    });

    Queue::assertNotPushed(SendAdminAlert::class);
}

// Run the job's handle() synchronously for full coverage
$job = new SendOrderConfirmation($order);
$job->handle();

Mail & Notification fakes with assertions

use Illuminate\Support\Facades\Mail;
use Illuminate\Support\Facades\Notification;

Mail::fake();
$this->createOrder($user);
Mail::assertSent(OrderConfirmation::class, fn ($mail) => $mail->hasTo($user->email));

Notification::fake();
$this->markOrderRefunded($order);
Notification::assertSentTo($user, OrderRefunded::class);
Real-life trap: with QUEUE_CONNECTION=sync in tests, a mailable becomes synchronous — it fires inside the controller. If you assert it was sent after a queue job would run, order your fakes and run the job explicitly first.

Real Problem #5: File Uploads

The bug: avatar upload endpoint writes to real storage/app/public during tests, fills disk, and tests fail on re-runs because files already exist. Also, huge "real" files slow the suite.

Storage::fake() + UploadedFile::fake()

use Illuminate\Http\UploadedFile;
use Illuminate\Support\Facades\Storage;

public function test_user_can_upload_avatar(): void
{
    Storage::fake('public');
    $user = User::factory()->create();
    $file = UploadedFile::fake()->image('avatar.png', 600, 600);

    $response = $this->actingAs($user)
        ->postJson('/api/avatar', ['avatar' => $file]);

    $response->assertOk();

    // File must physically exist on the fake disk
    Storage::disk('public')->assertExists('avatars/' . $user->id . '.png');

    // Invalid type / size rejection
    $badFile = UploadedFile::fake()->create('doc.txt', 100, 'text/plain');
    $this->actingAs($user)
        ->postJson('/api/avatar', ['avatar' => $badFile])
        ->assertUnprocessable();
}
Why Storage::fake: everything is written to a temporary directory that is wiped after each test — no disk pollution, no stale files, and you can assert on the exact stored path.

Real Problem #6: Auth & Authorization

The bug: "User A can edit User B's order" — a missing policy check. The test suite only had happy paths, so the privilege escalation shipped. Real apps need negative tests for every resource.

Sanctum::actingAs() for authenticated API calls

use Laravel\Sanctum\Sanctum;

public function test_user_can_view_own_order(): void
{
    $user = User::factory()->create();
    $order = Order::factory()->for($user)->create();

    Sanctum::actingAs($user);

    $this->getJson("/api/orders/{$order->id}")
        ->assertOk();
}

public function test_user_cannot_view_others_order(): void
{
    $user = User::factory()->create();
    $other = User::factory()->create();
    $order = Order::factory()->for($other)->create();

    Sanctum::actingAs($user);

    $this->getJson("/api/orders/{$order->id}")
        ->assertForbidden();
}

Policies keep the check out of the controller

final class OrderPolicy
{
    public function view(User $user, Order $order): bool
    {
        return $user->id === $order->user_id || $user->isAdmin();
    }
}

// Controller stays thin
public function show(Order $order): OrderResource
{
    $this->authorize('view', $order);

    return new OrderResource($order);
}
Test every branch of the policy as its own case: owner, admin, other user, guest. If a policy returns wrong for one branch, the API leaks data.

Real Problem #7: Parallel Tests & Shared State

The bug: you switch to php artisan test --parallel. Suddenly tests fail randomly: "unique constraint", "table not found". Cause: parallel workers share one SQLite :memory: database — each worker migrates and they clobber each other.

Give every worker its own database

// phpunit.xml - database name per process
<php>
    <env name="DB_CONNECTION" value="mysql"/>
    <env name="DB_DATABASE" value="testing_<unique-suffix>"/>
</php>

// For MySQL/Postgres use separate test DBs per worker, e.g.
//   DB_DATABASE=japapp_test_1, japapp_test_2 ... and refresh each

// Parallel execution
php artisan test --parallel

// Control how many processes
php artisan test --parallel --processes=8
Parallel gotchas: avoid tests that depend on global static state, avoid ordering between tests, use unique Faker values, and never rely on DatabaseTransactions + in-memory SQLite when workers share a file.

Avoid shared global state leaks

// Reset singleton/service state after each test
protected function tearDown(): void
{
    RateLimiter::clear('order-place:' . $this->userId);
    Cache::flush();

    parent::tearDown();
}

// Or scoped fakes in Pest
test('rate limit applies per user', function (): void {
    RateLimiter::for('order-place:' . $this->user->id, fn () => 5);

    foreach (range(1, 5) as $i) {
        $this->actingAs($this->user)->postJson('/api/orders', $this->payload)
            ->assertStatus(201);
    }

    $this->actingAs($this->user)->postJson('/api/orders', $this->payload)
        ->assertTooManyRequests();
});

API Routes & Versioning

Versioned routes with a prefix group

// routes/api.php
use Illuminate\Support\Facades\Route;

Route::prefix('v1')->name('v1.')->group(function (): void {
    // Public read endpoints (throttled)
    Route::get('/products', [ProductController::class, 'index'])
        ->middleware('throttle:products');

    // Authenticated, token-protected endpoints
    Route::middleware('auth:sanctum')->group(function (): void {
        Route::apiResource('orders', OrderController::class);
        Route::post('/orders/{order}/cancel', [OrderController::class, 'cancel']);
    });
});

// v2 later - additive, never breaking
Route::prefix('v2')->name('v2.')->group(function (): void {
    Route::apiResource('orders', \App\Http\Controllers\Api\V2\OrderController::class);
});
Real-life tip: version in the URL path for broad compatibility (mobile apps can't update headers easily). Keep old versions running and deprecate with a Deprecation header + sunset date, not instant removal.

Custom route model binding

// {order:number} binds by the 'number' column instead of id
Route::get('/orders/{order:number}', [OrderController::class, 'show']);

// Test it
public function test_show_by_number(): void
{
    $order = Order::factory()->create();

    $this->getJson("/api/orders/{$order->number}")
        ->assertOk()
        ->assertJsonPath('data.number', $order->number);
}

Form Requests: Validation You Can Test

A real order FormRequest with business rules

final class StoreOrderRequest extends FormRequest
{
    public function authorize(): bool
    {
        return $this->user()->can('place-orders');
    }

    public function rules(): array
    {
        return [
            'items'           => ['required', 'array', 'min:1'],
            'items.*.product_id' => ['required', 'integer', 'exists:products,id'],
            'items.*.quantity' => ['required', 'integer', 'between:1,99'],
            'coupon_code'    => ['nullable', 'string'],
            'shipping_address' => ['required', 'array'],
            'shipping_address.city' => ['required', 'string', 'max:120'],
            'shipping_address.zip'  => ['required', 'string', 'regex:/^[0-9]{5}$/'],
        ];
    }

    public function messages(): array
    {
        return [
            'items.min' => 'An order must contain at least one item.',
            'shipping_address.zip.regex' => 'The zip code must be 5 digits.',
        ];
    }
}
Real-life tip: assert validation messages in a feature test with assertJsonValidationErrors('items') so a typo in a message key or a rule that never fires surfaces the moment someone changes validation.

Business rule in a custom Rule object

final class ActiveCoupon implements ValidationRule
{
    public function validate(string $attribute, mixed $value, Closure $fail): void
    {
        $coupon = Coupon::query()
            ->where('code', $value)
            ->where('expires_at', '>', now())
            ->first();

        if ($coupon === null) {
            $fail('The :attribute is expired or invalid.');
        }
    }
}

// Unit-test the rule in isolation
public function test_expired_coupon_fails(): void
{
    $rule = new ActiveCoupon();
    $fail = fn (string $msg) => $this->assertSame('The coupon is expired or invalid.', $msg);

    $rule->validate('coupon_code', 'EXPIRED', $fail);
}

API Resources: Shape the Response

Conditional fields with whenLoaded / when

final class OrderResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'           => $this->id,
            'number'       => $this->number,
            'status'       => $this->status->value,
            'total'        => [
                'cents' => $this->total_cents,
                'formatted' => money($this->total_cents),
            ],
            'placed_at'    => $this->placed_at->toIso8601String(),
            // Only appear when the relationship was eager loaded
            'user'         => new UserResource($this->whenLoaded('user')),
            'items'        => OrderItemResource::collection($this->whenLoaded('items')),
            // Admin-only field
            'internal_notes' => $this->when($request->user()?->isAdmin(), $this->internal_notes),
        ];
    }
}
Common bug: returning $this->user unconditionally forces a lazy load inside the resource — even after you called with(), a nested resource that touches an un-loaded relation re-triggers N+1. whenLoaded() makes the contract explicit and testable.

Test the JSON contract, not just the status code

public function test_order_json_shape(): void
{
    $user = User::factory()->create();
    $order = Order::factory()
        ->for($user)
        ->has(OrderItem::factory()->count(2), 'items')
        ->create();

    $response = $this->actingAs($user)
        ->getJson("/api/orders/{$order->id}");

    $response->assertOk()
        ->assertJsonStructure([
            'data' => [
                'id', 'number', 'status',
                'total' => ['cents', 'formatted'],
                'items' => [['product_id', 'quantity', 'line_total']],
            ],
        ])
        ->assertJsonPath('data.status', 'pending');

    // Guard: unauthorized user must never see internal_notes
    $this->actingAs(User::factory()->create())
        ->getJson("/api/orders/{$order->id}")
        ->assertJsonMissingPath('data.internal_notes');
}

Filtering, Sorting & Pagination

public function index(Request $request): OrderCollection
{
    $orders = Order::query()
        ->with(['user', 'items'])
        ->when($request->filled('status'), fn ($q) => $q->where('status', $request->string('status')))
        ->when($request->boolean('mine'), fn ($q) => $q->where('user_id', $request->user()->id))
        ->when($request->filled('sort'), function ($q) use ($request): void {
            // Allowlist columns only - never raw input into orderBy
            $sort = in_array($request->string('sort'), ['placed_at', 'total_cents'], true)
                ? $request->string('sort') : 'placed_at';
            $dir  = $request->string('dir') === 'asc' ? 'asc' : 'desc';
            $q->orderBy($sort, $dir);
        })
        ->paginate($request->integer('per_page', 15));

    return new OrderCollection($orders);
}
Security trap: never do ->orderBy($request->input('sort')). A crafted value like id; DROP TABLE orders-- or an unknown column throws a 500. The allowlist above makes injection impossible and is easy to unit test.

Feature test for filter + pagination metadata

public function test_index_filters_and_paginates(): void
{
    $user = User::factory()->create();
    Order::factory()->count(30)->for($user)->create();
    Order::factory()->count(3)->for($user)->state(['status' => OrderStatus::Refunded])->create();

    $response = $this->actingAs($user)
        ->getJson('/api/orders?status=refunded&per_page=2');

    $response->assertOk()
        ->assertJsonCount(2, 'data')
        ->assertJsonPath('meta.total', 3)
        ->assertJsonPath('meta.last_page', 2);
}

Rate Limiting

// app/Providers/RouteServiceProvider.php - named limits
RateLimiter::for('api', function (Request $request): Limit {
    return $request->user()
        ? Limit::perMinute(60)->by($request->user()->id)
        : Limit::perMinute(10)->by($request->ip());
});

RateLimiter::for('order-place', fn (Request $r): Limit =>
    Limit::perMinute(5)->by($r->user()?->id ?: $r->ip())
);

// routes/api.php - attach by name
Route::post('/orders', [OrderController::class, 'store'])
    ->middleware('throttle:order-place');
Testing tip: with the array cache store, rate limits reset between tests automatically. Loop n times then assert 429 — this catches limits that are too tight (breaking legitimate users) or too loose (allowing abuse).

Consistent Error Handling

// app/Exceptions/Handler.php - render API errors in a stable shape
public function render(Request $request, Throwable $e): Response|JsonResponse
{
    if ($request->is('api/*') || $request->expectsJson()) {
        return $this->apiError($e);
    }

    return parent::render($request, $e);
}

private function apiError(Throwable $e): JsonResponse
{
    $status = 500; $code = 'server_error'; $message = 'Something went wrong.';

    if ($e instanceof ModelNotFoundException) {
        $status = 404; $code = 'not_found'; $message = 'Resource not found.';
    } elseif ($e instanceof AuthenticationException) {
        $status = 401; $code = 'unauthenticated';
    } elseif ($e instanceof AuthorizationException) {
        $status = 403; $code = 'forbidden';
    } elseif ($e instanceof ValidationException) {
        return $this->json([
            'error' => ['code' => 'validation_failed', 'fields' => $e->errors()],
        ], 422);
    }

    if (app()->isProduction()) {
        logger()->error('api_error', ['code' => $code, 'exception' => $e->getMessage()]);
    }

    return $this->json([
        'error' => ['code' => $code, 'message' => $message],
    ], $status);
}
Why clients care: a stable error.code lets mobile apps switch on logic (forbidden => logout), while a hidden stack trace prevents leaking internal paths and DB schemas in production.

Case Study: Order API With Full Tests

A complete, realistic vertical slice: routes → request → service → job → resource → tests. Read top to bottom and you can rebuild it.

1. Migration + Enums

// Schema for orders
Schema::create('orders', function (Blueprint $table): void {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->string('number')->unique();
    $table->string('status')->default('pending');
    $table->unsignedBigInteger('total_cents')->default(0);
    $table->timestamp('placed_at')->nullable();
    $table->timestamps();
});

// App\Enums\OrderStatus.php - backed enum
enum OrderStatus: string
{
    case Pending  = 'pending';
    case Paid     = 'paid';
    case Shipped  = 'shipped';
    case Refunded = 'refunded';
}

2. Service: the total is business logic, not controller code

final class OrderService
{
    public function place(User $user, array $items, ?string $couponCode): Order
    {
        $order = DB::transaction(function () use ($user, $items): Order {
            $order = $user->orders()->create([
                'number'    => 'ORD-' . str(Order::query()->max('id') + 1)->padLeft(6, '0'),
                'placed_at' => now(),
            ]);

            $total = 0;
            foreach ($items as $item) {
                $product = Product::findOrFail($item['product_id']);
                $line = $product->price_cents * $item['quantity'];
                $total += $line;

                $order->items()->create([
                    'product_id' => $product->id,
                    'quantity'   => $item['quantity'],
                    'unit_price_cents' => $product->price_cents,
                    'line_total_cents' => $line,
                ]);
            }

            $order->update(['total_cents' => $total]);

            return $order;
        });

        SendOrderConfirmation::dispatch($order);

        return $order;
    }
}

3. The queued job

final class SendOrderConfirmation implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;
    public int $backoff = 60;

    public function __construct(private readonly Order $order) {}

    public function handle(): void
    {
        Mail::to($this->order->user)->send(new OrderConfirmation($this->order));
    }

    public function failed(Throwable $e): void
    {
        logger()->error('OrderConfirmation failed', [
            'order' => $this->order->id,
            'error' => $e->getMessage(),
        ]);
    }
}

5. Feature test the endpoint

final class OrderEndpointTest extends TestCase
{
    use RefreshDatabase;

    protected OrderService $service;

    protected function setUp(): void
    {
        parent::setUp();
        $this->service = new OrderService();
    }

    public function test_authenticated_user_can_place_order(): void
    {
        Queue::fake([SendOrderConfirmation::class]);
        $user = User::factory()->create();
        $product = Product::factory()->create(['price_cents' => 2500]);

        $response = $this->actingAs($user)
            ->postJson('/api/v1/orders', [
                'items' => [
                    ['product_id' => $product->id, 'quantity' => 2],
                ],
                'shipping_address' => ['city' => 'Delhi', 'zip' => '110001'],
            ]);

        $response->assertCreated()
            ->assertJsonPath('data.total.cents', 5000)
            ->assertJsonPath('data.status', 'pending');

        Queue::assertPushed(SendOrderConfirmation::class, 1);
    }

    public function test_guest_cannot_place_order(): void
    {
        $this->postJson('/api/v1/orders', ['items' => []])
            ->assertUnauthorized();
    }

    public function test_order_rejects_empty_items(): void
    {
        $user = User::factory()->create();

        $this->actingAs($user)
            ->postJson('/api/v1/orders', [
                'items' => [],
                'shipping_address' => ['city' => 'Delhi', 'zip' => '110001'],
            ])
            ->assertUnprocessable()
            ->assertJsonValidationErrors('items');
    }

    public function test_rate_limit_applies_to_ordering(): void
    {
        $user = User::factory()->create();
        $product = Product::factory()->create();

        foreach (range(1, 5) as $i) {
            $this->actingAs($user)->postJson('/api/v1/orders', $this->payload($product))
                ->assertCreated();
        }

        $this->actingAs($user)->postJson('/api/v1/orders', $this->payload($product))
            ->assertTooManyRequests();
    }
}

Best Practices & Checklist

The one rule that prevents most bugs: every public API behavior has at least one positive test and one negative test (guest, other user, expired, too long, malformed). If a new route has no negative test, it will leak data.
Testing Checklist
  • Prevent lazy loading in non-production
  • Freeze time with travelTo()
  • Fake every external dependency
  • Test JSON shape, not just status
  • Negative tests for authz on every resource
  • Isolated DB per parallel worker
  • Coverage gate at 85% in CI
API Checklist
  • Version in the URL path
  • FormRequest per write action
  • Business logic in services/policies
  • Eager load before resources run
  • Allowlist for sort/filter columns
  • Named rate limits per endpoint
  • Stable error codes, no stack traces
