The Big Picture

CodeIgniter is the lightweight PHP MVC framework that traded magic for speed — tiny footprint, nearly zero configuration, and a manual that fits in one page. The catch: version 4 was a complete rewrite, so the framework's history is really two different frameworks sharing a name. Version 1–3 are one lineage (super-object, no namespace, no Composer); version 4 is a modern PSR-4 framework with namespaces and CLI tooling.

The four eras at a glance
VersionReleasedPHPStatusArchitecture
1.x2006PHP 4DeadProcedural-era MVC, no namespaces
2.x2011PHP 5.1+DeadSuper-object, drivers, packages

The one thing to remember: there is no automatic upgrade from CI3 to CI4. A composer update will never get you there. CI4 is a different framework with the same philosophy — plan a migration, not an upgrade.

Era 1 — CI 1.x (2006–2011)

01

The spark

EOL — historic
Released by EllisLab in February 2006 as an open-source alternative to heavier PHP frameworks. Made its name on tiny footprint and speed: one config file, no templating engine, load-everything-you-need. It ran on PHP 4, which mattered enormously in 2006.
PHP 4.x Notable $this->load->model(), active record Status historic
  • Introduced the $this-> super-object pattern that defined CI1–CI3.
  • Introduced Active Record (the Query Builder's ancestor).
  • No namespaces, no autoloader — you loaded libraries by hand.

Era 2 — CI 2.x (2011–2015)

02

The PHP 5 era

EOL — historic
Dropped PHP 4 for good and required PHP 5.1.6+. Added drivers (one interface, multiple backends — sessions, cache), packages for library organization, and a rewritten session class. This is the era that made CI the most-downloaded PHP framework for a stretch.
PHP 5.1.6+ Notable drivers, packages, Session rewrite Status historic
  • Most code written for CI2 moves to CI3 with almost no changes — they are one lineage.
  • Legacy CI2 projects still run on old shared hosts today; that's the dangerous part.

Era 3 — CI 3.x (2015–2022)

03

The classic

EOL — Oct 2022
CI3 is the version most "CodeIgniter code" in the wild is written in. It kept the super-object model but modernized the plumbing: PHP 5.6+ (later 7.x compatible), a real session class (no more cookies-only), password hashing via password_hash(), encryption, and better security defaults. Security patches ended October 2022 — then a final 3.1.13 dropped support entirely.
PHP 5.6+ (7.x OK) Notable sessions, bcrypt, SPARKS Status unsupported since 2022
If you maintain CI3 today, you are running unsupported code. No more security fixes. It still works, but it should not touch the internet without a migration plan.

Era 4 — CI 4.x (2020 → now)

04

The modern rewrite

ACTIVE — 4.7.4
Released February 2020 by the CodeIgniter Foundation (the British Columbia Institute of Technology took over stewardship from EllisLab). A ground-up rewrite on modern PHP:
  • Namespaces everywhere — PSR-4 autoloading, App\Controllers\*
  • Composer — composer create-project codeigniter4/appstarter
  • Spark CLI — php spark serve, generators, migrations
  • Services pattern — db_connect(), session(), model()
  • Entity / Model ORM-style layer (not Doctrine, but real)
  • Filters (route-level middleware) and a proper $routes file
  • Built-in web server for local dev
PHP 7.4+ (now 8.2+) Notable Spark, Composer, namespaces, filters Status actively maintained

CI3 → CI4 Migration Path

Moving from 3.x to 4.x is a rewrite with a map. The good news: every concept maps to something familiar. Do it in this order.

  1. Start from the app starter. Do not carry your old folder over. composer create-project codeigniter4/appstarter myapp
  2. Move your controllers into app/Controllers with namespaces (namespace App\Controllers;) and extend BaseController.
  3. Move views into app/Views. Replace $this->load->view() with echo view() / return view().
  4. Rebuild models as App\Models\* extending Model, and load them with model('UserModel') instead of $this->load->model().
  5. Port your SQL from Active Record to the Query Builder — it is nearly 1:1.
  6. Replace all $this->input-> calls with the request object ($this->request->getPost(), getGet()).
  7. Replace $this->session-> with the session() service.
  8. Recreate your routes in app/Config/Routes.php using the new $routes->get() syntax.
  9. Move config into namespaced Config classes; environment stuff into .env.
  10. Test every page — then delete the old application/ folder.

The most common CI3 expressions and their CI4 equivalents — print this one.

$this->load->view('page')echo view('page') // or return view()
$this->input->post('name')$this->request->getPost('name')
$this->input->get('q')$this->request->getGet('q')

CI4 → CI4 Minor Upgrades

Upgrading within 4.x is the easy path — the official docs publish a per-version upgrade page.

Standard procedure
# 1. Back up (or commit) first
git status && git commit -am "before upgrade"

# 2. Bump the framework version in composer.json
composer require codeigniter4/framework:"^4.7" --with-all-dependencies
composer update

# 3. Run the app in dev mode and check the Debug Toolbar
php spark serve

# 4. Test routes, forms, and auth flows
php spark test

# 5. Check the upgrade notes for Config changes
#    e.g. 4.7 changed some Config defaults — update app/Config/*
Known break pointsWhat to check
PHP requirement bump4.5→PHP 8.1, 4.7→PHP 8.2 — verify host PHP first
Config changesNew/changed defaults in app/Config; env keys renamed
Session / cookie handlingEncrypted cookies & handler changes in 4.5+
Cache engine4.4 reworked cache; check cache drivers config
Deprecated methods removedRun php spark debug:deprecations in dev

Which Version to Use

Starting new?
  • Use 4.7.x on PHP 8.3+
  • Install via composer create-project codeigniter4/appstarter
  • Follow 4.x idioms: namespaces, services, Filters
  • For APIs use the RESTful controllers + setJSON()
Inherited CI3?
  • It has been unsupported since Oct 2022
  • Plan a CI4 migration — budget it as a rewrite
  • Do not install any "upgrade plugin" — there isn't one
  • If it's internal-only with no web exposure, you have time — but not forever
Bottom line: CodeIgniter survives because it stays small. Use 4.x for new work, treat any 3.x project as an unsupported liability, and use the tables above as your PHP-versus-version checklist before you touch a server.
