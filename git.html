Git

Complete Command Reference & Practical Use Cases v2.x Linus Torvalds 2005 — Present

Git is the industry-standard distributed version control system. This guide covers every essential command, real-world use cases, and workflow patterns from basic commits to advanced debugging — all with practical examples.

Setup & Configuration

First-Time Setup
# Identity — required for commits
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

# Default branch name
git config --global init.defaultBranch main

# Editor
git config --global core.editor "code --wait"

# Line endings (Windows)
git config --global core.autocrlf true

# Line endings (macOS/Linux)
# git config --global core.autocrlf input

# Aliases — shortcuts for common commands
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all --decorate"

Basic Commands

Every Git user's daily toolkit — starting a repo, staging, committing, and inspecting.

Starting a Repository

CommandUse Case

Staging & Committing

CommandUse Case
git add <file>Stage a specific file
git add .Stage all changes in current directory
git add -pInteractive staging — stage parts of a file (hunks)
git rm <file>Remove a file and stage the deletion
git mv <old> <new>Rename a file and stage it
git commit -m "message"Commit staged changes with inline message
git commit -am "message"Stage all tracked files + commit (skip git add)
git commit --amendAmend last commit (add staged changes / edit message)
git commit --allow-empty -m "message"Create an empty commit (trigger CI, mark milestones)

Status & Inspection

CommandUse Case
git statusShow working tree status (modified, staged, untracked)
git status -sShort status — one line per file
git diffView unstaged changes (working tree vs index)
git diff --stagedView staged changes (index vs last commit)
git diff <branchA>..<branchB>Compare two branches
git show <commit>Show the diff and metadata of a specific commit
git show HEADShow the latest commit details
Pro Tip: Use git add -p to commit only specific lines of a file. This keeps your commits atomic — each commit does exactly one logical change. For large refactors, it's invaluable for code review.

Branching & Merging

The heart of Git — isolated development lines, feature branches, and integration.

CommandUse Case
git branchList local branches (current branch highlighted)
git branch -aList all branches (local + remote)
git branch <name>Create a new branch (stays on current)
git branch -d <name>Delete a merged branch
git branch -D <name>Force delete a branch (unmerged changes)
git branch -m <old> <new>Rename a branch
git checkout -b <name>Create and switch to a new branch
git switch <name>Switch to an existing branch (newer syntax, Git 2.23+)
git switch -c <name>Create and switch (newer syntax)
git merge <branch>Merge <branch> into current branch
git merge --no-ff <branch>Merge with no fast-forward (preserves branch history)
git merge --squash <branch>Squash all branch commits into one (no merge commit)
git merge --abortAbort a merge with conflicts
Best Practice: Use switch / restore (Git 2.23+) instead of the overloaded checkout. The newer commands separate branch-switching from file-restoring, reducing the chance of mistakes.

Remote Operations

Push, pull, fetch, and collaborate with remote repositories.

CommandUse Case
git remote add origin <url>Add a remote named origin
git remote -vList remote URLs (fetch + push)
git remote remove <name>Remove a remote
git remote rename <old> <new>Rename a remote
git remote set-url origin <url>Change remote URL (e.g., HTTPS → SSH)
git fetch <remote>Download objects/refs without merging
git fetch --pruneFetch and remove stale remote-tracking branches
git pullFetch + merge (or rebase if configured)
git pull --rebaseFetch + rebase (cleaner linear history)
git pushPush local commits to remote
git push -u origin <branch>Push and set upstream tracking
git push --force-with-leaseForce push safely (won't overwrite others' work)
git push origin --delete <branch>Delete a remote branch
git push --tagsPush all tags to remote
⚡ Safety First: Never use git push --force. Always use git push --force-with-lease — it checks that your remote-tracking branch is up to date and won't clobber commits you haven't seen.

Undoing Changes

Fix mistakes at every stage — before staging, after staging, after committing, and after pushing.

Unstaging & Discarding

CommandUse Case
git restore <file>Discard unstaged changes in working tree (Git 2.23+)
git restore --staged <file>Unstage a file (keep working tree changes)
git restore --source=HEAD <file>Restore file to last committed state
git checkout -- <file>Discard unstaged changes (older syntax)
git reset HEAD <file>Unstage a file (older syntax)
git clean -fdRemove untracked files and directories

Undoing Commits

CommandUse Case
git reset --soft HEAD~1Undo last commit, keep changes staged
git reset --mixed HEAD~1Undo last commit, unstage changes (default)
git reset --hard HEAD~1Undo last commit, discard changes ⚠️
git revert <commit>Create a new commit that undoes a previous one (safe for public history)
git revert --no-commit <commit>Revert without auto-committing (revert multiple in one commit)
🛑 Rule of Thumb: git reset rewrites history — use only on local/unpushed commits. git revert is the safe choice for commits already pushed to shared branches.

Stash

Temporarily shelve changes when you need to switch context or pull in updates without committing half-finished work.

CommandUse Case
git stash push -m "message"Stash tracked changes with a description
git stash push -u -m "msg"Stash including untracked files
git stash listList all stashes
git stash popApply and remove the most recent stash
git stash apply stash@{2}Apply a specific stash without removing it
git stash drop stash@{1}Delete a specific stash
git stash clearRemove all stashes
git stash branch <name> stash@{0}Create a branch from a stash
Stash Tip: Always use git stash push -m "description" instead of bare git stash. When you have 10 stashes, "WIP on main" is useless — "WIP: login form validation fixed" tells you exactly what's saved.

Rebasing & Cherry-Pick

Rewrite commit history for a cleaner, linear project timeline.

Rebase

CommandUse Case
git rebase mainReapply current branch commits on top of main
git rebase -i HEAD~3Interactive rebase — squash, reword, reorder last 3 commits
git rebase --abortAbort a rebase in progress
git rebase --continueContinue rebase after resolving conflicts
git rebase --skipSkip a problematic commit during rebase
git rebase --onto main feature~3 featureMove a branch's root to a different point

Cherry-Pick

CommandUse Case
git cherry-pick <commit>Apply a single commit from another branch
git cherry-pick A..BApply a range of commits (A is excluded, B is included)
git cherry-pick -n <commit>Cherry-pick without auto-committing
Interactive Rebase Cheat Sheet (git rebase -i):
pick — use commit as-is  |  reword — change message  |  squash — combine into previous  |  fixup — squash, discard message  |  drop — delete commit  |  edit — stop to amend

Git Hooks

Shell scripts that run automatically on specific Git events. Stored in .git/hooks/. Rename .sample files to activate.

HookWhen It RunsUse Case
pre-commitBefore commit message editorLint code, run tests, check for secrets
prepare-commit-msgAfter default message is createdInject issue tracker IDs, prefix with branch name
commit-msgAfter user edits messageEnforce commit message format (Conventional Commits)
post-commitAfter commit completesSend notification, update CI
pre-pushBefore push executesRun full test suite, prevent force-push to protected branches
pre-receiveServer-side, before ref updateEnforce branch policies, reject large files
updateServer-side, per refFine-grained branch/tag ACL
post-receiveServer-side, after ref updateCI trigger, deploy, update chat
Modern Approach: Instead of raw shell hooks, use Husky (JS) or pre-commit (Python) to manage hooks per-repo with shareable config. They version-control the hook scripts so every developer gets the same setup.

Git Workflows

Standard branching strategies for teams of any size.

GitHub Flow Simple

main → feature branch → PR → merge

  1. Branch from main
  2. Commit changes
  3. Open a pull request
  4. Code review + CI passes
  5. Merge to main
  6. Deploy immediately
Best for: Continuous deployment, simple projects, small teams.
Git Flow Structured

main + develop + feature + release + hotfix

  • main — production-ready code only
  • develop — integration branch
  • feature/* — branched from develop
  • release/* — branched from develop, merged to both
  • hotfix/* — branched from main
GitLab Flow Env Branches

main → environment branches

  • main — latest stable
  • staging — pre-production
  • production — deployed version
  • Merge upstream (main → staging → production)
  • Each environment branch deploys automatically
Trunk-Based Fast

Short-lived branches → main

  • Feature branches live < 1 day
  • Frequent small commits to main
  • Feature flags hide incomplete work
  • No long-running release branches
  • CI runs on every push
Best for: CI/CD, DevOps, large engineering orgs (Google, Netflix).

Bisect — Real-World Bug Hunting

# Step 1: Start bisect
git bisect start
# Step 2: Mark current (broken) and a known-good commit
git bisect bad
git bisect good v1.0
# Step 3: Git checks out a middle commit. Test it.
# If it's good:
git bisect good
# If it's bad:
# git bisect bad
# Step 4: Repeat step 3 until Git identifies the exact commit
# Step 5: Clean up
git bisect reset

Reflog — The Safety Net

Lost a commit? Reset the wrong branch? Reflog saves you. It records every HEAD movement for 90 days.

# View the entire recent history of HEAD
git reflog

# Restore a "lost" commit (e.g., after a bad reset)
git reflog           # find the commit hash
git cherry-pick <hash>   # or git branch recover-branch <hash>
Bisect Automation: Run git bisect run <script> to fully automate bisect. Pass a script that exits 0 (good) or non-0 (bad). Git will binary-search overnight and wake up with the culprit commit.

Best Practices

Commit Hygiene
  • One logical change per commit
  • Imperative commit messages: "Add login" not "Added login"
  • Subject ≤ 50 chars, body wrapped at 72
  • Reference issues: "Fix #42: handle edge case"
  • No "fix typo" commits — squash into logical commit
  • Atomic commits make git bisect and git revert reliable
Branch Management
  • Delete merged branches: git branch -d
  • Use descriptive names: feat/payment-gateway, fix/login-crash
  • Rebase feature branches before merging to main
  • Squash messy WIP commits before pushing PR
  • Protect main branch — require PR reviews + CI
Safety & Security
  • Never commit secrets, .env, or API keys
  • Add a .gitignore from the start
  • Use --force-with-lease, never bare --force
  • Use signed commits (git commit -S) for OSS
  • Run git secrets or talisman as a pre-commit hook
  • If a secret was pushed — rotate it immediately
Team Collaboration
  • Adopt Conventional Commits (feat:, fix:, chore:)
  • Keep PRs small — reviewable in < 30 minutes
  • Use PR templates for consistent descriptions
  • Rebase, don't merge, to keep history linear
  • Write meaningful code review comments
  • Agree on one workflow (GitHub Flow / Git Flow)

Troubleshooting

Common problems and their fixes.

ProblemSolution
"Commit your changes or stash them" 🔹 git stash push -m "temp" — stash, then pull/rebase, then git stash pop
Merge conflict 🔹 Edit conflicted files → git add → git commit
🔹 Or use git mergetool
Committed to wrong branch 🔹 git reset HEAD~1 → git switch correct-branch → git add . && git commit
Accidentally reset --hard 🔹 git reflog → find the lost commit → git cherry-pick <hash> or git reset --hard <hash>
Pushed a commit with a secret 🔹 Rotate the secret immediately. Then git filter-repo or git filter-branch to purge from history
"Detached HEAD" state 🔹 git branch temp → git switch temp (creates a branch to save your work)
"There is no tracking information" 🔹 git branch -u origin/branch or git push -u origin branch
"You are not currently on a branch" 🔹 git checkout -b new-branch to keep changes, or git switch - to go back
Large file committed accidentally 🔹 git filter-repo --path <file> --invert-paths to remove from history (then force push)
Forgot to add a file in last commit 🔹 git add forgotten-file && git commit --amend --no-edit
