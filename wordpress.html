Introduction

What is WordPress Development?

WordPress is PHP + MySQL underneath the hood. Any custom work happens in one of two places: a theme (presentation — what pages look like) or a plugin (behavior — what the site can do). Both listen to hooks so core stays updatable while your custom code stays your own.

Theme

Templates, loops, CSS & JS. Lives in wp-content/themes/. Changes presentation only.

Plugin

CPTs, hooks, REST routes, blocks. Lives in wp-content/plugins/. Adds behavior and features.

Hooks

Actions and filters. The glue that lets both themes and plugins extend core without editing it.

Theme vs Plugin concept
ConcernThemePlugin
JobPresentation — how content rendersBehavior — what the site does
Locationwp-content/themes/<theme>/wp-content/plugins/<plugin>/
SwappingSwitch theme = layout changesDeactivate = feature disappears
Should containTemplates, styling, enqueuesLogic, CPTs, settings, integrations
Data loss riskHigh if you put CPTs/logic hereNone — data survives theme changes
Rule of thumbDesign changes onlyEverything reusable & site-critical
The golden rule: never store behavior that a site depends on inside a theme. When a client switches themes, they should keep their posts, products, CPTs and custom fields. Custom content types and business logic belong in a plugin; the theme only dresses them up.
Step 01 — Setup

Local Environment & WP-CLI

A local install is enough to start: WP-CLI is the fastest way to scaffold a site, a theme, and a plugin from the terminal. It works on top of XAMPP/MAMP, Local WP, or any PHP + MySQL stack.

Fresh install with WP-CLI bash
# 1. Download WordPress into the current directory

wp core download

# 2. Create wp-config.php from the sample

wp config create --dbname=myapp --dbuser=root --dbpass= --dbhost=localhost

# 3. Install the site (creates tables + admin user)

wp core install \
  --url=http://localhost/myapp \
  --title="My App" \
  --admin_user=admin \
  --admin_password=secret \
  --admin_email=me@example.com

# 4. Start coding â€” scaffold a theme and a plugin

wp scaffold child-theme mytheme --parent_theme=twentytwentyfive
wp scaffold plugin myplugin

Step 02 — Hooks

Actions & Filters

Hooks are the entire WordPress extension API. An action fires at a point in time (do something there); a filter passes a value through a function that may change it. Everything else — themes, plugins, blocks — is just code attached to hooks.

Action php
add_action( 'wp_footer', 'my_analytics' );

function my_analytics() {
  // Runs before </body> on every page.
  echo '<script>/* tracking */</script>';
}
Filter php
add_filter( 'excerpt_length', fn () => 30 );

add_filter( 'the_title', function ( $title ) {
  return sprintf( '%s &middot; %s', $title, get_bloginfo( 'name' ) );
}, 10, 1 );
Signature & priority php
// add_action / add_filter share the same signature:
//    $hook, $callback, $priority (default 10), $accepted_args (default 1)

add_action( 'init', 'my_early',  5 );   // runs first
add_action( 'init', 'my_late',   99 );  // runs last

// Remove a hook someone else registered:
remove_action( 'wp_footer', 'my_analytics' );
remove_filter( 'excerpt_length', 'other_callback', 10 );
Firing your own hooks php
// Give other developers extension points inside your plugin:

do_action( 'myplugin_before_save', $post_id, $args );

$price = apply_filters( 'myplugin_price', $base_price, $product );
Hooks you will live in reference
HookTypeWhen it fires
initactionAfter WP is loaded; register CPTs, taxonomies, rewrite rules
wp_enqueue_scriptsactionFront-end scripts & styles (public site)
admin_enqueue_scriptsactionBackend scripts & styles
wp_head / wp_footeractionInside <head> / before </body>
save_postactionRight after a post is saved (hook your meta-box handler here)
the_contentfilterPost content, right before output
the_titlefilterPost title before it prints
excerpt_length / excerpt_morefilterShape generated excerpts
pre_get_postsactionAlter main queries before they run
admin_menuactionRegister admin menu pages
plugins_loadedactionAll plugins loaded â€” safe to reference other plugins
after_setup_themeactionTheme features (add_theme_support())
Plugins loaded, then theme, then core. mu-plugins run first, then active plugins (plugins_loaded), then the theme (after_setup_theme). Load order matters when two hooks depend on each other.
Step 03 — Themes

Theme Setup & Functions.php

A theme is identified by the header comment in style.css. Everything it does starts in functions.php, which runs on every request. Keep it to feature-declaration and enqueueing — not site logic.

style.css header css
/*
Theme Name:   MyTheme
Theme URI:    https://example.com/mytheme
Author:       You
Description:  A custom theme for the guide.
Version:      1.0.0
Text Domain:  mytheme
*/
functions.php â€” features & enqueues php
if ( ! function_exists( 'mytheme_setup' ) ) :
function mytheme_setup() {
    load_theme_textdomain( 'mytheme', get_template_directory() . '/languages' );

    add_theme_support( 'title-tag' );               // let WP print <title>
    add_theme_support( 'post-thumbnails' );          // featured images
    add_theme_support( 'custom-logo', [
        'height'      => 80,
        'width'       => 240,
        'flex-width'  => true,
    ] );
    add_theme_support( 'html5', [ 'search-form', 'gallery', 'caption' ] );
    add_theme_support( 'responsive-embeds' );
}
endif;
add_action( 'after_setup_theme', 'mytheme_setup' );

function mytheme_assets() {
    wp_enqueue_style( 'mytheme-fonts', 'https://fonts.googleapis.com/css2?family=...', [], null );
    wp_enqueue_style( 'mytheme-style', get_stylesheet_uri(), [], wp_get_theme()->get( 'Version' ) );

    wp_enqueue_script( 'mytheme-main', get_template_directory_uri() . '/js/main.js', [], null, true );
}
add_action( 'wp_enqueue_scripts', 'mytheme_assets' );

Child themes

Child theme â€” safe customization css
/* style.css in the child theme: */
/*
Theme Name:  MyTheme Child
Template:    mytheme
Text Domain: mytheme-child
*/

/* Override parent styles from here */
// functions.php in the child theme â€” load parent styles first:
add_action( 'wp_enqueue_scripts', function () {
    wp_enqueue_style( 'parent-style', get_template_directory_uri() . '/style.css' );
} );
Edit the child, not the parent. A child theme inherits all parent templates but lets you override any file by dropping the same name into the child folder. Parent updates never clobber your changes.
Step 04 — Themes

The Template Hierarchy

WordPress picks a template file by walking a fixed list of candidates from most specific to most generic. You only need to ship the files you care about — anything missing falls back to index.php.

The chain for a single post resolution

single-post.php          // <-- highest priority
single.php
singular.php
index.php               // the ultimate fallback

Step 05 — Themes

The Loop & WP_Query

The Loop is the standard pattern: fetch a query, loop its posts, print each one. The default query is already set up by the time a template runs; use a secondary WP_Query for custom lists and pre_get_posts to reshape the main query.

The Loop â€” index.php php
<?php while ( have_posts() ) : the_post(); ?>

<article <?php post_class(); ?>>
    <h2><a href="<?php the_permalink(); ?>"><?php the_title(); ?></a></h2>
    <?php the_excerpt(); ?>
</article>

<?php endwhile; ?>

<?php
the_posts_pagination();
?>
Secondary query â€” latest 3 news php
$news = new WP_Query( [
    'post_type'      => 'post',
    'category_name'  => 'news',
    'posts_per_page' => 3,
    'no_found_rows'  => true,  // skip pagination count â€” faster
] );

while ( $news->have_posts() ) : $news->the_post(); ?>
    <h3><?php the_title(); ?></h3>
<?php endwhile;

wp_reset_postdata();  // restore the main query's current post
pre_get_posts â€” reshape the main query php
add_action( 'pre_get_posts', function ( WP_Query $query ) {
    if ( $query->is_main_query() && ! is_admin() && $query->is_archive() ) {
        $query->set( 'posts_per_page', 12 );
    }
} );
Never use a secondary WP_Query where pre_get_posts can do it. The main query is already built and paginated by WP; overriding it is cheaper and keeps URLs, pagination and caching consistent.
Step 06 — Themes

Customizer & Post Meta

Themes expose appearance settings through the Customizer (stored as theme mods or options), and per-post fields through meta boxes. Both are small, well-worn APIs.

Add a Customizer setting + control php
add_action( 'customize_register', function ( $wp_customize ) {

    $wp_customize->add_section( 'mytheme_colors', [
        'title'    => __( 'Theme Colors', 'mytheme' ),
        'priority' => 30,
    ] );

    $wp_customize->add_setting( 'mytheme_accent', [
        'default'           => '#2271b1',
        'sanitize_callback' => 'sanitize_hex_color',
    ] );

    $wp_customize->add_control( 'wp_color_control', [
        'label'   => __( 'Accent', 'mytheme' ),
        'section' => 'mytheme_colors',
        'settings' => 'mytheme_accent',
    ] );
} );

// Read it anywhere in templates:
$accent = get_theme_mod( 'mytheme_accent', '#2271b1' );
Meta box â€” a "tagline" field php
add_action( 'add_meta_boxes', function () {
    add_meta_box( 'post_tagline', __( 'Tagline' ), 'render_tagline', 'post' );
} );

function render_tagline( $post ) {
    wp_nonce_field( 'save_tagline', 'tagline_nonce' );
    $value = get_post_meta( $post->ID, '_tagline', true );
    echo '<input type="text" name="tagline" value="' .
        esc_attr( $value ) . '" class="widefat">';
}

add_action( 'save_post', function ( $post_id ) {
    if ( ! isset( $_POST['tagline_nonce'] ) ||
         ! wp_verify_nonce( $_POST['tagline_nonce'], 'save_tagline' ) ) {
        return;
    }
    if ( defined( 'DOING_AUTOSAVE' ) && DOING_AUTOSAVE ) return;

    $clean = sanitize_text_field( $_POST['tagline'] ?? '' );
    update_post_meta( $post_id, '_tagline', $clean );
} );
Prefix meta keys with _ to hide them from the Custom Fields screen and to keep them out of front-end meta queries. Always pass a sanitize_callback on settings and sanitize every meta value on save.

Menus & Widgets

Register menu locations and widget areas (sidebars) in the theme, then print them with template tags. Users manage the actual contents from the admin.

Register menus php
add_action( 'after_setup_theme', function () {

} );

// In header.php:
<?php
wp_nav_menu( [
    'theme_location' => 'primary',
    'container'      => 'nav',
    'fallback_cb'     => false,
] );
?>
Register a widget area php
add_action( 'widgets_init', function () {
    register_sidebar( [
        'name'          => __( 'Sidebar', 'mytheme' ),
        'id'            => 'sidebar-1',
        'before_widget' => '<div id="%1$s" class="widget %2$s">',
        'after_widget'  => '</div>',

Step 08 — Plugins

Plugin Basics

A plugin is any folder with a PHP file whose header names the plugin. The header makes it appear in the admin Plugins screen; lifecycle hooks let you clean up on activate, deactivate, and uninstall.

myplugin/myplugin.php â€” header + lifecycle php
<?php
/**
 * Plugin Name: My Plugin
 * Description: A sample plugin for the guide.
 * Version:     1.0.0
 * Author:      You
 * Text Domain: myplugin
 */

// Prevent direct access.
if ( ! defined( 'ABSPATH' ) ) exit;

// Activation: fire once on first activation.
register_activation_hook( __FILE__, function () {
    add_option( 'myplugin_activated', current_time( 'mysql' ) );
    // Set default options, flush rewrite rules, etc.
} );

// Deactivation: stop scheduled jobs, remove temp data.
register_deactivation_hook( __FILE__, function () {
    wp_clear_scheduled_hook( 'myplugin_daily' );
} );

// Uninstall: run only when the plugin is deleted, not deactivated.
// (Put this in an uninstall.php file, never in the main file.)
Suggested plugin structure files
myplugin/
  myplugin.php          # bootstrap: header + require files + hooks
  uninstall.php         # cleanup when the plugin is deleted
  includes/
    class-post-type.php # each concern = one class/file
    class-settings.php
    class-shortcode.php
  admin/                # admin-only code
  public/               # front-end code
  assets/css/ js/       # compiled assets
  languages/            # translation files
Single class pattern php
class MyPlugin {

    private static $instance = null;

    public static function instance(): self {
        if ( null === self::$instance ) {
            self::$instance = new self();
        }
        return self::$instance;
    }

    private function __construct() {
        add_action( 'init', [ $this, 'register' ] );
        add_action( 'wp_enqueue_scripts', [ $this, 'enqueue' ] );
    }

    public function register() {
        // CPTs, taxonomies, rewrite rules...
    }
}

MyPlugin::instance();
Keep plugin code out of the global namespace. Use classes and namespaces. One class per responsibility (post type, settings, REST routes) makes the plugin testable and lets you conditionally load files only where they run.
Step 09 — Plugins

Options & the Settings API

Simple key/value storage uses get_option / update_option. For admin settings pages, the Settings API handles the form, nonces, and sanitization for you — write a page, sections, and fields, and register the option.

Reading & writing options php
$enabled = get_option( 'myplugin_enabled', false );  // 2nd arg = default
update_option( 'myplugin_enabled', true );
delete_option( 'myplugin_enabled' );

// Autoload = fetched on every request. Keep light values autoload=yes, heavy arrays = no.
add_option( 'myplugin_big', $data, '', 'no' );
Settings page with the Settings API php
add_action( 'admin_menu', function () {
    add_options_page( __( 'My Plugin' ), __( 'My Plugin' ), 'manage_options', 'myplugin', 'myplugin_settings_page' );
} );

add_action( 'admin_init', function () {
    register_setting( 'myplugin_group', 'myplugin_enabled', [
        'type'              => 'boolean',
        'sanitize_callback' => 'rest_sanitize_boolean',
    ] );

    add_settings_section( 'myplugin_section', __( 'General' ), null, 'myplugin' );

    add_settings_field( 'myplugin_enabled', __( 'Enable feature' ),
        'myplugin_enabled_field', 'myplugin', 'myplugin_section' );
} );

function myplugin_settings_page() {
    ?>
    <div class="wrap">
        <h1><?php esc_html_e( 'My Plugin Settings' ); ?></h1>
        <form method="post" action="options.php">
            <?php settings_fields( 'myplugin_group' ); ?>
            <?php do_settings_sections( 'myplugin' ); ?>
            <?php submit_button(); ?>
        </form>
    </div>
    <?php
}

function myplugin_enabled_field() {
    printf( '<input type="checkbox" name="myplugin_enabled" value="1" %s>',
        checked( get_option( 'myplugin_enabled', false ), true, false ) );
}
Never save unsanitized input. Every option registered with the Settings API gets its sanitize_callback run automatically on save. If you write your own form instead, run check_admin_referer() and call the sanitizer yourself.
Step 10 — Plugins

Custom Post Types & Taxonomies

CPTs let content editors create non-post content (products, events, testimonials), each with its own admin menu, archive, and template files. Taxonomies group them, exactly like categories and tags.

Register a CPT on init php
add_action( 'init', function () {
    register_post_type( 'product', [
        'labels' => [
            'name'          => __( 'Products' ),
            'singular_name' => __( 'Product' ),
            'add_new_item'  => __( 'Add New Product' ),
        ],
        'public'       => true,
        'has_archive'  => true,
        'menu_icon'    => 'dashicons-cart',
        'supports'     => [ 'title', 'editor', 'thumbnail', 'excerpt' ],
        'show_in_rest'  => true,   // needed for the block editor
    ] );

    register_taxonomy( 'product_type', 'product', [
        'labels'  => [ 'name' => __( 'Product Types' ) ],
        'hierarchical' => true,
        'show_in_rest' => true,
    ] );
} );
Rewrite rules & flushing php
// register_post_type creates /product/ and /product/{slug}/ URLs.
// After changing rewrite args, flush once on activation:

register_activation_hook( __FILE__, function () {
    myplugin_register_cpt();
    flush_rewrite_rules();
} );

// Templates: single-product.php, taxonomy-product_type.php, archive-product.php
Querying a CPT php
$featured = new WP_Query( [
    'post_type'      => 'product',
    'product_type'   => 'featured',   // taxonomy filter
    'posts_per_page' => 6,
    'meta_key'       => '_price',
    'orderby'        => 'meta_value_num',
    'order'          => 'ASC',
] );
Register CPTs and taxonomies in a plugin, not a theme. When the theme changes, the content type must survive. Prefer native supports and show_in_rest over heavy plugins so the block editor keeps working.
Step 11 — Plugins

Security Essentials

WordPress gives you the tools; using them is non-negotiable. Four rules cover almost every exploit: nonce every form, check capabilities on every protected action, sanitize on input, and escape on output.

Nonces & capabilities php
// Verify a submitted form (POST). Dies on failure.
check_admin_referer( 'save_tagline', 'tagline_nonce' );

// Non-die alternative for AJAX:
if ( ! wp_verify_nonce( $_POST['_nonce'] ?? '', 'myaction' ) ) {
    wp_die( 'Bad nonce' );
}

// Guard any protected action with a capability:
if ( ! current_user_can( 'edit_posts' ) ) {
    wp_die( 'Not allowed' );
}
Sanitize in, escape out php
// INPUT â€” sanitize before saving:
$title = sanitize_text_field( $_POST['title'] );
$id    = absint( $_POST['post_id'] );

// OUTPUT â€” escape before echoing:
esc_html( $title );         // plain text
esc_attr( $value );         // inside an attribute
esc_url( $url );           // links
esc_textarea( $body );     // textarea content
wp_kses_post( $html );      // allow safe HTML like the editor
Prepared SQL with $wpdb php
global $wpdb;

// Never interpolate user input into SQL â€” always prepare():
$count = $wpdb->get_var( $wpdb->prepare(
    "SELECT COUNT(*) FROM {$wpdb->posts} WHERE post_type = %s AND post_status = %s",
    'product',
    'publish'
) );

Security checklist

Every form gets a nonce (wp_nonce_field() + check_admin_referer() or wp_verify_nonce()).
Capability-check every AJAX handler and settings action (current_user_can()).
Sanitize all input with the right sanitize_*() function; use $wpdb->prepare() for SQL.
Escape all output with esc_*() or wp_kses*() — never echo raw $_POST/$_GET.
Validate files (wp_check_filetype(), check_ajax_referer()) before uploads.
Run esc_html__() for translations so translated strings can't inject HTML.
Step 12 — Advanced

REST API & AJAX

For dynamic front-ends, prefer the WP REST API (/wp-json/wp/v2/...) â€” clean URLs, built-in auth, JSON everywhere. The legacy admin-ajax.php endpoint still exists and is the common path for quick form handlers.

Custom REST route php
add_action( 'rest_api_init', function () {
    register_rest_route( 'myplugin/v1', '/products/(?P<id>\d+)', [
        'methods'             => WP_REST_Server::READABLE,
        'callback'            => 'myplugin_get_product',
        'permission_callback' => 'myplugin_check_read',
    ] );
} );

function myplugin_get_product( WP_REST_Request $request ) {
    $post = get_post( $request['id'] );
    if ( ! $post ) {
        return new WP_Error( 'not_found', 'No product.', [ 'status' => 404 ] );
    }
    return rest_ensure_response( [
        'id'    => $post->ID,
        'title' => get_the_title( $post ),
    ] );
}

function myplugin_check_read() {
    return true;  // or current_user_can() for protected data
}
admin-ajax handler php
add_action( 'wp_ajax_my_vote',        'myplugin_vote' );  // logged in
add_action( 'wp_ajax_nopriv_my_vote', 'myplugin_vote' );  // guests

function myplugin_vote() {
    check_ajax_referer( 'vote', 'nonce' );
    // do the work...
    wp_send_json_success( [ 'votes' => 42 ] );
}
Pass the AJAX URL to JS php
wp_localize_script( 'myplugin-front', 'MyPlugin', [
    'ajax_url' => admin_url( 'admin-ajax.php' ),
    'nonce'    => wp_create_nonce( 'vote' ),
] );
// front.js
fetch( MyPlugin.ajax_url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: 'action=my_vote&nonce=' + MyPlugin.nonce,
} );
Prefer the REST API for new code. Admin-ajax is untidy for public endpoints and famously easy to fat-finger. REST gives you typed routes, JSON, and authentication out of the box â€” use it unless you only need a tiny logged-in form action.
Step 13 — Advanced

Shortcodes & Gutenberg Blocks

Shortcodes are the classic way to embed dynamic content in the editor. Modern plugins register blocks with block.json so editors get a real UI; a render_callback keeps the PHP logic server-side.

A shortcode php
add_shortcode( 'pricing', 'myplugin_pricing' );

function myplugin_pricing( $atts ) {
    $atts = shortcode_atts( [ 'plan' => 'basic' ], $atts );
    $price = get_option( 'price_' . sanitize_key( $atts['plan'] ) );
    return '<span class="price">' . esc_html( $price ) . '</span>';
}

// Usage: [pricing plan="pro"]
A server-rendered block php
// blocks/pricing/block.json
{
  "apiVersion": 3,
  "name": "myplugin/pricing",
  "title": "Pricing",
  "attributes": { "plan": { "type": "string", "default": "basic" } },
  "render": "block-render.php"
}
// blocks/pricing/block-render.php
<?php
$price = get_option( 'price_' . sanitize_key( $attributes['plan'] ) );
?>
<span class="price"><?php esc_html( $price ); ?></span>
Register the block folder once. In the plugin bootstrap call register_block_type( __DIR__ . '/blocks/pricing' ) — WP reads block.json, loads editor assets, and uses your render callback. No npx @wordpress/create-block build step is required for server-rendered blocks.
Step 14 — Advanced

Performance

Enqueue assets only where they run, cache expensive work with transients, and keep the options table lean. A few conventions keep a custom site fast without a caching plugin.

Cache a heavy result with transients php
function myplugin_expensive_data() {
    $cached = get_transient( 'myplugin_report' );
    if ( false !== $cached ) {
        return $cached;
    }

    // Build the data (slow query, external API call...)
    $data = myplugin_build_report();

    set_transient( 'myplugin_report', $data, DAY_IN_SECONDS );
    return $data;
}

// Invalidate when the source changes:
delete_transient( 'myplugin_report' );

  • Theme = presentation; plugin = behavior. Never mix.

  • Prefix every CPT, option, meta key, and hook name
  • Nonce every form; capability-check every protected action
  • Sanitize input, escape output, prepare SQL
  • Cache expensive work in transients; invalidate on change
  • Flush rewrite rules on activation, not every request
  • Use __()/esc_html__() for translatable strings
