Symfony

Complete Command Reference & Concept Guide v7.x PHP 8.2+ Released Nov 2024

Symfony is a high-performance PHP framework built on reusable, decoupled components. This guide covers all console commands, core concepts, Doctrine ORM, Twig templating, and a detailed Symfony vs Laravel comparison.

Installation

# Create a new Symfony project with Composer
composer create-project symfony/skeleton myapp

# Or use the Symfony CLI (recommended)
symfony new myapp --full
symfony new myapp --webapp

# Install Maker bundle (dev helper)
composer require --dev symfony/maker-bundle

# Install Doctrine ORM
composer require symfony/orm-pack

# Install Twig
composer require symfony/twig-pack

# Install API Platform
composer require api-platform/core

# Start the dev server
symfony server:start

# Start with HTTPS
symfony server:start --no-tls

MVC Architecture

Symfony follows the Model-View-Controller pattern with a clear directory structure.

Model

Doctrine entities, repositories and business logic in src/Entity/

View

Twig templates in templates/ — reusable, extendable blocks

Controller

Request handlers in src/Controller/ returning responses

Default Directory Structure
myproject/
├─ assets/               # Webpack Encore / Vite assets
├─ bin/
│─   console              # CLI entry point
├─ config/
│─   packages/            # Bundle config (YAML/ PHP)
│─   services.yaml         # Service container config
├─ migrations/            # Doctrine migrations
├─ public/
│─   index.php             # Front controller
├─ src/
│─   Controller/           # Controllers
│─   Entity/               # Doctrine entities
│─   Repository/           # Doctrine repositories
│─   Form/                 # Form types
│─   EventSubscriber/      # Event subscribers
│─   Security/             # Voters, authenticators
│─   Twig/                 # Twig extensions
│─   Kernel.php            # App kernel
├─ templates/              # Twig templates
├─ translations/          # Message translations
├─ .env                   # Environment variables
├─ composer.json
├─ symfony.lock           # Flex lock file
Symfony Flex: Uses recipes to auto-configure bundles when packages are installed. Running composer require automatically adds config files, updates bundles, and registers routes.

Controllers

Controllers extend AbstractController and return Response objects. Symfony auto-wires services via type-hints.

namespace App\Controller;

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

class ProductController extends AbstractController
{
    public function __construct(
        private ProductRepository $repository,
        private SerializerInterface $serializer,
    ) {}

    #[Route('/products', name: 'product_list')]
    public function list(Request $request): Response
    {
        $products = $this->repository->findAll();

        return $this->render('product/list.html.twig', [
            'products' => $products,
        ]);
    }

    #[Route('/products/{id}', name: 'product_show')]
    public function show(int $id): Response
    {
        $product = $this->repository->find($id);

        if (!$product) {
            throw $this->createNotFoundException();
        }

        return $this->json($product, 200, [], [
            'groups' => ['product:read'],
        ]);
    }
}
Key Difference from Laravel: Symfony controllers rely on constructor injection for dependencies, while Laravel uses app() helper or method injection. Symfony also returns explicit Response objects rather than using facades.

Dependency Injection Container

Symfony's DI container is one of its most powerful features. Services are configured via config/services.yaml and auto-wired automatically.

services.yaml — Service Configuration
# config/services.yaml
parameters:
    app.admin_email: 'admin@example.com'

services:
    # Default configuration for services in src/
    App\:
        resource: '../src/'
        exclude:
            - '../src/DependencyInjection/'
            - '../src/Entity/'
            - '../src/Kernel.php'

    # Explicit service configuration
    App\Service\MailService:
        arguments:
            $adminEmail: '%app.admin_email%'
        tags: ['app.mail_service']

    # Aliasing an interface to a concrete class
    App\Interface\PaymentInterface:
        alias: 'App\Service\StripePayment'
        public: true

Doctrine ORM

Doctrine is Symfony's default ORM. Entities are plain PHP objects with attributes mapping them to database tables.

Entity Example

namespace App\Entity;

use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity(repositoryClass: ProductRepository::class)]
#[ORM\Table(name: 'products')]
class Product
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column(type: 'integer')]
    private int $id;

    #[ORM\Column(type: 'string', length: 255)]
    private string $name;

    #[ORM\Column(type: 'text', nullable: true)]
    private ?string $description = null;

    #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
    private float $price;

    #[ORM\Column(type: 'datetime_immutable')]
    private DateTimeImmutable $createdAt;

    // Getters and setters...
    public function getId(): int { return $this->id; }
    public function getName(): string { return $this->name; }
    public function setName(string $name): self { ... }
    // ...
}

Repository

namespace App\Repository;

use Doctrine\Bundle\DoctrineBundle\Repository\ServiceEntityRepository;
use Doctrine\Persistence\ManagerRegistry;

class ProductRepository extends ServiceEntityRepository
{
    public function __construct(ManagerRegistry $registry)
    {
        parent::__construct($registry, Product::class);
    }

    public function findByPriceRange(float $min, float $max): array
    {
        return $this->createQueryBuilder('p')
            ->andWhere('p.price BETWEEN :min AND :max')
            ->setParameter('min', $min)
            ->setParameter('max', $max)
            ->orderBy('p.price', 'ASC')
            ->getQuery()
            ->getResult();
    }
}

Query Builder vs DQL

Query Builder
$qb = $this->createQueryBuilder('p');

$qb->select('p')
    ->where('p.price > :price')
    ->setParameter('price', 100)
    ->orderBy('p.name', 'ASC')
    ->setMaxResults(10);

$results = $qb->getQuery()
    ->getResult();
DQL (Doctrine Query Language)
$dql = 'SELECT p FROM App\Entity\Product p
         WHERE p.price > :price
         ORDER BY p.name ASC';

$query = $this->getEntityManager()
    ->createQuery($dql)
    ->setParameter('price', 100)
    ->setMaxResults(10);

$results = $query->getResult();
Key Difference from Laravel: Doctrine uses the Data Mapper pattern (entities are plain POPOs), while Eloquent uses Active Record (models extend a base class). Doctrine entities need getters/setters; Eloquent models expose properties directly. Doctrine's Query Builder uses DQL; Eloquent uses a PHP query builder.

Associations (Relationships)

Doctrine supports the same relationship types as Eloquent, but they are defined via attributes on entity properties.

ManyToOne / OneToMany
// Category has many Products
#[ORM\OneToMany(
    mappedBy: 'category',
    targetEntity: Product::class,
    cascade: ['persist', 'remove']
)]
private Collection $products;

// Product belongs to Category
#[ORM\ManyToOne(inversedBy: 'products')]
#[ORM\JoinColumn(nullable: false)]
private ?Category $category = null;
ManyToMany
// Student has many Courses
#[ORM\ManyToMany(targetEntity: Course::class)]
#[ORM\JoinTable(name: 'students_courses')]
private Collection $courses;

// Usage:
$student->getCourses()->add($course);
$this->getEntityManager()->flush();
OneToOne
// User has one Profile
#[ORM\OneToOne(
    targetEntity: Profile::class,
    mappedBy: 'user',
    cascade: ['persist', 'remove']
)]
private ?Profile $profile = null;
Inverse Side (MappedBy)
// Profile belongs to User (inverse side)
#[ORM\OneToOne(inversedBy: 'profile')]
#[ORM\JoinColumn(name: 'user_id', referencedColumnName: 'id')]
private ?User $user = null;
Key Difference from Laravel: In Doctrine, you must explicitly define both sides of a relationship (owning side with JoinColumn, inverse side with mappedBy). Laravel's Eloquent handles this automatically with convention-based foreign keys. Doctrine requires Collection type hints; Eloquent uses Collection return types from relationship methods.

Validation

Symfony's Validator component provides assertion-based validation via Attributes, YAML, or XML.

Entity Validation with Attributes

use Symfony\Component\Validator\Constraints as Assert;

class Product
{
    #[Assert\NotBlank]
    #[Assert\Length(min: 3, max: 255)]
    private string $name;

    #[Assert\NotBlank]
    #[Assert\PositiveOrZero]
    #[Assert\Type('numeric')]
    private float $price;

    #[Assert\Email(message: 'The email {{ value }} is not valid.')]
    private ?string $contactEmail = null;

    #[Assert\Url]
    private ?string $website = null;
}

Validating in Controller

use Symfony\Component\Validator\ValidatorInterface;

#[Route('/products/new', methods: ['POST'])]
public function new(
    Request $request,
    ValidatorInterface $validator
): Response
{
    $product = new Product();
    $product->setName($request->get('name'));

    $errors = $validator->validate($product);

    if (count($errors) > 0) {
        return $this->json([
            'errors' => (string) $errors,
        ], 400);
    }

    // ... persist and return
}

Form Validation

use Symfony\Component\Form\Extension\Core\Type\TextType;

class ProductFormType extends AbstractType

    public function buildForm(FormBuilderInterface $builder, array $options)
    {
        $builder

Twig Templates

Twig is Symfony's default templating engine — a modern, secure, and extensible template language.

Base Layout (base.html.twig)
{# templates/base.html.twig #}
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>{% block title %}My App{% endblock %}</title>
    {% block stylesheets %}{% endblock %}
</head>
<body>
    {% block header %}
        <nav>...</nav>
    {% endblock %}

    <main>
        {% block body %}{% endblock %}
    </main>

    {% block javascripts %}{% endblock %}
</body>
</html>
Child Template (product/list.html.twig)
{# templates/product/list.html.twig #}
{% extends 'base.html.twig' %}

{% block title %}Product List{% endblock %}

{% block body %}
    <h1>Products</h1>

    <table>
        {% for product in products %}
            <tr>
                <td>{{ product.name }}</td>
                <td>{{ product.price|number_format(2) }}</td>
            </tr>
        {% else %}
            <tr><td colspan="2">No products found.</td></tr>
        {% endfor %}
    </table>
{% endblock %}

Twig Features

FeatureSyntaxDescription
Variables{{ variable }}Echo a variable (auto-escaped)
Filters{{ name|upper }}Chainable filters (|date, |json_encode)
For loops{% for item in items %}Iterate over arrays/objects
If/else{% if condition %}Conditional rendering
Extends{% extends 'base.html.twig' %}Template inheritance
Include{{ include('_card.html.twig') }}Include partial templates

Key Difference from Laravel: Twig uses {{ }} for output and {% %} for logic. Blade uses {{ }} for output and @directive syntax. Twig is stricter (no PHP in templates), while Blade allows raw PHP. Twig has sandboxing for security; Blade relies on Laravel's escaping.

Security

Symfony's Security component is a comprehensive, firewall-based authentication and authorization system.

User Entity

namespace App\Entity;

use Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface;
use Symfony\Component\Security\Core\User\UserInterface;

class User implements UserInterface, PasswordAuthenticatedUserInterface
{
    #[ORM\Column(type: 'string', length: 180, unique: true)]
    private string $email;

    #[ORM\Column(type: 'json')]
    private array $roles = [];

    #[ORM\Column(type: 'string')]
    private string $password;

    public function getRoles(): array
    {
        $roles = $this->roles;
        $roles[] = 'ROLE_USER';
        return array_unique($roles);
    }

    public function eraseCredentials() {}
}

Security Configuration (config/packages/security.yaml)

# config/packages/security.yaml
security:
    password_hashers:
        App\Entity\User: 'auto'

    providers:
        app_user_provider:
            entity:
                class: App\Entity\User
                property: 'email'

    firewalls:
        main:
            lazy: true
            provider: 'app_user_provider'
            form_login:
                login_path: 'app_login'
                check_path: 'app_login'
            logout:
                path: 'app_logout'

    access_control:
        - { path: '^/admin', roles: ROLE_ADMIN }
        - { path: '^/profile', roles: ROLE_USER }

Authorization (Voters)

use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Authorization\Voter\Voter;

class ProductVoter extends Voter
{
    public const VIEW = 'view';
    public const EDIT = 'edit';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, [self::VIEW, self::EDIT])
            && $subject instanceof Product;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();

        return $user === $subject->getOwner();
    }
}

// In controller:
$this->denyAccessUnlessGranted('edit', $product);
Key Difference from Laravel: Symfony uses firewall-based authentication with YAML configuration, while Laravel uses middleware-based auth with auth middleware. Symfony's Voters are analogous to Laravel's Policies but use a class-based voting system rather than simple methods. Symfony's security.yaml is more explicit; Laravel uses AuthServiceProvider and config/auth.php.

Messenger (Queue / Jobs)

Symfony Messenger provides a message bus with middleware, transport, and async processing.

Message & Handler

// src/Message/SendWelcomeEmail.php
class SendWelcomeEmail
{
    public function __construct(
        public readonly int $userId,
    ) {}
}

// src/MessageHandler/SendWelcomeEmailHandler.php
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
class SendWelcomeEmailHandler
{
    public function __invoke(SendWelcomeEmail $message): void
    {
        // Process the message
        $this->mailer->send(/* ... */);
    }
}

// In controller - dispatch message
use Symfony\Component\Messenger\MessageBusInterface;

$this->bus->dispatch(new SendWelcomeEmail($user->getId()));

Messenger Configuration

# config/packages/messenger.yaml
framework:
    messenger:
        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'  # Doctrine, AMQP, Redis
                options:
                    queue_name: 'default'
            failed:
                dsn: 'doctrine://default?queue_name=failed'

        routing:
            App\Message\SendWelcomeEmail: 'async'

Running the Worker

# Consume messages from the async transport
php bin/console messenger:consume async --limit=10

# Run in background as a daemon
php bin/console messenger:consume async -vv

# List failed messages
php bin/console messenger:failed:show

# Retry failed messages
php bin/console messenger:failed:retry --force
Key Difference from Laravel: Symfony Messenger uses a message bus pattern with separate Message + Handler classes. Laravel uses Job classes with a handle() method. Symfony supports multiple transports (Doctrine, AMQP, Redis, SQS) with automatic routing. Laravel's queue system uses trait-based dispatch (dispatch() helper). Both support retries, delays, and failure handling.

API Platform

API Platform is a full-stack API framework built on top of Symfony, providing REST and GraphQL support automatically.

Basic API Resource

namespace App\Entity;

use ApiPlatform\Metadata\ApiResource;
use Symfony\Component\Serializer\Attribute\Groups;

#[ApiResource(
    operations: [
        new Get(),
        new GetCollection(),
        new Post(),
        new Put(),
        new Delete(),
    ],
    normalizationContext: ['groups' => ['product:read']],
    denormalizationContext: ['groups' => ['product:write']],
)]
class Product
{
    #[Groups(['product:read', 'product:write'])]
    #[ORM\Column(type: 'string', length: 255)]
    private string $name;

    #[Groups(['product:read'])]
    private float $price;
}

Custom API Controller

use ApiPlatform\Metadata\ApiResource;
use ApiPlatform\Metadata\Post;

#[ApiResource(
    operations: [
        new Post(
            uriTemplate: '/products/{id}/publish',
            controller: PublishProductController::class,
            deserialize: false,
        ),
    ],
)]
class Product { /* ... */ }

// Custom controller
class PublishProductController
{
    public function __invoke(Product $data): Product
    {
        $data->setPublished(true);
        return $data;
    }
}
Key Difference from Laravel: Symfony's API Platform provides automatic REST/GraphQL from entity attributes — no manual controller setup for CRUD. Laravel requires explicit route definitions (apiResource) and controller methods. API Platform also auto-generates OpenAPI docs, Swagger UI, and Mercure real-time updates.

Mailer

Symfony Mailer provides a powerful mail abstraction with support for multiple transports.

use Symfony\Component\Mailer\MailerInterface;
use Symfony\Component\Mime\Email;

class OrderConfirmationService
{
    public function __construct(
        private MailerInterface $mailer,
    ) {}

    public function send(Order $order): void
    {
        $email = (new Email())
            ->from('orders@example.com')
            ->to($order->getCustomerEmail())
            ->subject('Order Confirmation #' . $order->getId())
            ->text($this->renderText($order))
            ->html($this->renderHtml($order));

        $this->mailer->send($email);
    }
}
# config/packages/mailer.yaml
framework:
    mailer:
        dsn: 'smtp://user:pass@smtp.example.com:587?encryption=tls'
        # Or use mailpit for development:
        # MAILER_DSN=smtp://127.0.0.1:1025
        # Or sendmail:
        # MAILER_DSN=sendmail://default
Key Difference from Laravel: Symfony Mailer uses builder pattern with Email objects and DSN-based transport configuration. Laravel uses fluent Mail::to() facade and Mailable classes. Both support attachments, templates, and queues. Symfony's DSN format is more explicit; Laravel uses config/mail.php.

Serializer

Symfony's Serializer component handles converting objects to/from JSON, XML, YAML, CSV, and more.

use Symfony\Component\Serializer\SerializerInterface;
use Symfony\Component\Serializer\Attribute\Groups;
use Symfony\Component\Serializer\Attribute\MaxDepth;

class Product
{
    #[Groups(['product:read', 'product:write'])]
    private string $name;

    #[Groups(['product:read'])]
    #[MaxDepth(1)]
    private Category $category;
}

// In controller:
$json = $this->serializer->serialize($product, 'json', [
    'groups' => ['product:read'],
]);

$product = $this->serializer->deserialize(
    $json, Product::class, 'json'
);
Key Difference from Laravel: Symfony's Serializer is a standalone component using normalization/denormalization with group-based serialization. Laravel uses Eloquent API Resources (Resource/ResourceCollection) and ->toArray() with $this->when() conditionals. Symfony's approach is more declarative; Laravel's is more imperative and closer to the model layer.

Events & Middleware

Symfony provides two separate systems: the EventDispatcher for domain events and the HTTP Kernel for request/response middleware.

Event Subscriber

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;
use Symfony\Component\HttpKernel\KernelEvents;

#[AsEventListener(event: KernelEvents::EXCEPTION)]
class ExceptionSubscriber
{
    public function __invoke(ExceptionEvent $event): void
    {
        $exception = $event->getThrowable();

        if ($exception instanceof AccessDeniedException) {
            $event->setResponse(
                new JsonResponse(['error' => 'Forbidden'], 403)
            );
        }
    }
}

// Or use EventSubscriberInterface for multiple events:
class OrderSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [
            OrderCreatedEvent::class => ['onOrderCreated', 0],
            OrderShippedEvent::class => 'onOrderShipped',
        ];
    }

    public function onOrderCreated(OrderCreatedEvent $event): void { /* ... */ }
}

HTTP Kernel Middleware (Event Listeners)

# config/packages/framework.yaml
framework:
    early_events: true

// Kernel Events order:
// 1. kernel.request      - Request object created
// 2. kernel.controller   - Controller resolved
// 3. kernel.controller_arguments - Arguments resolved
// 4. kernel.view         - View returned (before response)
// 5. kernel.response     - Response object created
// 6. kernel.finish_request - Request completed
// 7. kernel.terminate    - After response sent
// 8. kernel.exception    - On uncaught exception
Key Difference from Laravel: Symfony uses the EventDispatcher component and kernel events for middleware-like behavior. Laravel uses dedicated Middleware classes with handle() method and $next($request) closure. Symfony events are dispatched throughout the request lifecycle; Laravel middleware wraps the entire request in a pipeline. Symfony's approach is more granular; Laravel's is simpler to grasp.

}
Key Difference from Laravel: Symfony uses PHPUnit directly with KernelTestCase and WebTestCase base classes. Laravel uses PHPUnit too, but provides TestCase with helper methods like $this->get(), $this->post(), $this->assertDatabaseHas(). Symfony's testing is more explicit about booting the kernel; Laravel's is more expressive with fluent assertions.

Symfony Standards: Follow Symfony Best Practices and Symfony Coding Standards. Use Attributes over YAML/annotations for routing, validation, and serialization. Prefer constructor injection over property injection.
Structure & Code

  • Use constructor injection for dependencies
  • Follow PSR-4 autoloading and PSR-12 coding style
  • Use DTOs (Data Transfer Objects) for form/API input
  • Prefer value objects over primitive types
  • Use Symfony Flex recipes for bundle configuration
  • Write unit and functional tests for all services
Security & Performance
  • Use Voters for complex authorization logic
  • Use Messenger for long-running tasks (async)

  • Use Doctrine second-level cache for read-heavy apps

  • Use HTTP cache (ESI/Fragment) for high-traffic pages

  • Use PHP attributes over annotations (deprecated)

Symfony vs Laravel: Head-to-Head Comparison

A comprehensive comparison of the two leading PHP frameworks. Both are excellent choices — the best one depends on your project needs and team expertise.

Symfony
  • Company: SensioLabs / Symfony Community
  • First Release: 2005 (Symfony 1.x)
  • Latest: 7.x (PHP 8.2+)
  • ORM: Doctrine (Data Mapper)
  • Templating: Twig
  • Config: YAML/XML/PHP Attributes
  • License: MIT
  • Philosophy: "Best tool for each job" — decoupled, reusable components
Laravel
  • Company: Laravel LLC / Taylor Otwell
  • First Release: 2011 (Laravel 1)
  • Latest: 13.x (PHP 8.3+)
  • ORM: Eloquent (Active Record)
  • Templating: Blade
  • Config: PHP files + .env
  • License: MIT
  • Philosophy: "The PHP Framework for Web Artisans" — expressive, elegant syntax
Feature-by-Feature Comparison
Feature Symfony Laravel
Architecture Decoupled components. Use only what you need via Flex recipes. Full-stack or micro-framework. Monolithic with modular service providers. Everything included out of the box.
ORM Pattern Data Mapper — Entities are plain POPOs. A separate EntityManager handles persistence. Requires explicit flush(). Active Record — Each model IS a database row. Methods like save(), delete() directly affect the DB. Implicit persistence.
Configuration YAML/XML/PHP — config/packages/*.yaml files. Explicit bundle configuration. Flex auto-configures packages. PHP & .env — config/*.php files return arrays. Convention-based configuration with env() helper.
Routing PHP Attributes on controller methods. YAML/XML/annotations also supported. Explicit route naming. Attributes on controller methods OR routes/web.php with Route:: facade. Convention resource() helper.
Templating Twig — Sandboxed, strict. {{ }} for output, {% %} for logic. No PHP in templates by design. Blade — {{ }} for escaped output, @directives for logic. Allows raw PHP. Lighter learning curve.
Dependency Injection Explicit YAML/PHP config in services.yaml. Auto-wiring is automatic for type-hinted services. Tags for service discovery. Auto-discovery in AppServiceProvider. bind(), singleton() methods. Facades provide static proxy to services.
Authentication Firewall-based in security.yaml. Authenticators, voters, password hashers. Very granular and explicit. Middleware-based with auth middleware. make:auth scaffolding. Passport/Sanctum for API auth. Simpler setup.
Authorization Voters — class-based voting with supports() and voteOnAttribute(). Granular per-object permissions. Policies & Gates — Gate::authorize() or $this->authorize(). Policies are methods on a class.
Queue / Async Messenger — Message + Handler pattern. Multiple transports (Doctrine, AMQP, Redis, SQS). Middleware stack per bus. Queue — Job classes with handle() method. dispatch() helper. Horizon for Redis monitoring.
API API Platform — Auto-generates REST/GraphQL from entity attributes. OpenAPI docs, Swagger, Mercure, pagination, filters included. Laravel Sanctum / API Resources — Manual controller setup with apiResource. Resource classes for transformation.
Validation Attributes on entity properties (#[Assert\NotBlank]). Validator service. Form types with embedded constraints. validate() method or FormRequest classes. Rule objects. $request->validate([...]) in controllers.
Database Migrations DoctrineMigrations — Auto-generated from entity changes via make:migration. Version-controlled SQL. Migration classes — up()/down() with Schema Builder. make:migration creates skeleton.
Testing PHPUnit with KernelTestCase and WebTestCase. Panther for browser testing. Explicit kernel booting. PHPUnit with TestCase providing fluent helpers: $this->get(), $this->assertDatabaseHas(). Laravel Dusk for browser.
Console Commands php bin/console with make:* commands (Maker bundle). debug:* commands for introspection. php artisan with make:* commands. Extensive built-in commands. list for overview.
Asset Management Webpack Encore or Vite with Symfony UX. importmap for simple JS. Stimulus + Turbo for SPA-like UX. Vite (Laravel 11+) or Mix (legacy). Inertia.js for SPA-like UX. Livewire for dynamic components.
Performance Profile Very fast in production (heavy caching). Higher Cold-start overhead. Excellent for large enterprise apps. Fast out of the box. Lighter cold-start. Great for rapid prototyping to mid-size apps. Can scale with proper caching.
Learning Curve Steeper. Requires understanding DI, EventDispatcher, Voters, Firewalls, etc. More concepts to learn. Gentler. Facades, Eloquent, and Artisan make it approachable. "Convention over configuration" philosophy.
Ecosystem Symfony UX, API Platform, EasyAdmin, Sonata Admin, Sylius (ecommerce), Shopware. Strong enterprise presence. Laravel Nova, Spark, Cashier, Horizon, Telescope, Forge, Vapor, Jetstream, Filament. Strong startup/SMB presence.
Community Larger in Europe. Used by Drupal, phpMyAdmin, Composer, Magento. Conferences: SymfonyCon. Largest PHP community globally. Conferences: Laracon. Most GitHub stars, StackOverflow questions, YouTube tutorials.
Choose Symfony When...
  • You need a fully decoupled, customizable architecture
  • Building long-lived enterprise applications
  • You need API Platform — auto-generated REST/GraphQL
  • Your team prefers explicit configuration over convention
  • You need multi-tenant or complex security setups
  • Working on a reusable bundle or open-source component
  • You value long-term support and backward compatibility
  • Integrating with existing Doctrine-based systems
Choose Laravel When...
  • You want rapid development with minimal boilerplate
  • Building MVP / startup products quickly
  • Your team is smaller or less experienced with OOP
  • You prefer convention over configuration
  • You need Livewire or Inertia for dynamic UIs
  • You want Horizon for queue monitoring, Telescope for debugging
  • You use Laravel Forge/Vapor for deployment
  • You want the largest hiring pool of PHP developers
Bottom Line: Both frameworks are production-ready and capable of building any PHP application. Symfony excels in enterprise environments where decoupling, customization, and long-term maintainability are critical. Laravel excels in rapid development, startup velocity, and developer happiness. Neither is "better" — choose the one that aligns with your team's skills and project requirements.
