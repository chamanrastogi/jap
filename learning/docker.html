Docker

One image, the same app everywhere Containers since 2013 · OCI standard Compose v2 · BuildKit

Docker packages your app and everything it needs — the right PHP, the right Node, the right extensions — into an image, then runs that image as an isolated container. "Works on my machine" stops being a sentence. This guide goes from your first docker run to a hardened, multi-stage build you would actually deploy, with the commands and the failure modes written next to each other.

What Docker Actually Is

Three words get mixed up constantly: image, container, and volume. Learn them once and the rest of Docker is just flags.

The three nouns
NounWhat it isAnalogy
ImageA read-only template: filesystem layers plus a start commandA class, or a .zip of a whole machine
ContainerA running (or stopped) instance of an image, with its own writable layerAn object created from that class
VolumeStorage that lives outside the container's lifeA USB stick you plug into it
an image, top to bottom

Each instruction adds one layer. Docker caches every layer and reuses it until the instruction or its inputs change.

The mental model that fixes 80% of confusion: a container is not a small computer. It is one process (plus its children) that the kernel has lied to about being alone. If that process exits, the container is dead — even if the machine is fine.

Install & First Run

Docker Desktop on Windows and macOS bundles the engine, Compose and a small Linux VM. On a Linux server you install the engine directly.

Verify the install
# client + server versions
docker version

# engine details, storage driver, resources
docker info

# the smallest possible smoke test
docker run --rm hello-world

# Compose is a plugin now: "docker compose", not "docker-compose"
docker compose version

Run something real in one line

# nginx on http://localhost:8080, deleted when stopped
docker run --rm -d --name web -p 8080:80 nginx:1.27-alpine

# look inside it (a shell in a container)
docker exec -it web sh

# follow its logs, then stop it
docker logs -f web
docker stop web
Lifecycle commands you will type every day
CommandWhat it does
docker run IMAGECreate and start a container from an image
docker ps -aList containers, including stopped ones
docker start / stop / restart NAMEControl an existing container
docker rm NAMEDelete a stopped container (-f to force)

docker logs --tail 100 -f NAMERead its stdout/stderr

docker statsLive CPU, memory and network per container
docker cp NAME:/path ./hereCopy files out of (or into) a container
Always name your containers in development (--name app). Random names like focused_turing make the next twenty commands a memory test.

Images & Containers in Practice

The commands that move an image around

# download from a registry (Docker Hub by default)
docker pull mysql:8.4

# what do I have locally?
docker images

# build an image from ./Dockerfile and tag it
docker build -t myapp:1.0 .

# copy a tag, then push it somewhere
docker tag myapp:1.0 ghcr.io/acme/myapp:1.0
docker push ghcr.io/acme/myapp:1.0

# inspect without running it
docker image inspect mysql:8.4
docker history myapp:1.0      # layer sizes, biggest last
docker image prune -a         # delete unused images

What actually persists?

Written to…Survives restart?Survives docker rm?
Container writable layerYesNo
Named volumeYesYes, until docker volume rm
Bind mount (host folder)YesYes — it is just your folder
tmpfs mountNoNo
Anything sent to stdoutIn docker logsNo
Rule: if it matters after the container dies — database files, uploads, sessions on disk — it must be in a volume or a bind mount. The writable layer is a scratch pad, not storage.

The Dockerfile

A Dockerfile is a recipe read top to bottom. One instruction per line, one layer per instruction. Here is a production-shaped Node image:

Dockerfile — Node 22, multi-stage, non-root
# ---------- build stage ----------
FROM node:22-alpine AS build
WORKDIR /app

# copy manifests first so this layer caches
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

# ---------- runtime stage ----------
FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY --from=build /app/dist ./dist

RUN addgroup -S app && adduser -S app -G app
USER app

EXPOSE 3000
CMD ["node", "dist/server.js"]

Every instruction, in one table

InstructionWhat it does — and the trap
FROMBase image. Pin a minor version (php:8.4-fpm), not latest.
WORKDIRCreates and enters a directory. Use it instead of RUN cd.
COPYFiles from build context. Cannot copy from outside it (../ fails).
ADDLike COPY, plus URL and tar extraction. Prefer COPY unless you need that.
RUNExecutes at build time, result is baked into a layer. Chain with && and clean up in the same line.
ENVPersists at run time and build time. Baked into the image — never secrets.
ARGBuild-time only, gone after the build. Still visible in docker history.
EXPOSEDocumentation only. It does not publish the port; -p does.
CMDDefault command — replaced by anything after the image name in docker run.
ENTRYPOINTFixed executable; CMD becomes its default arguments.
USERDrop root. Set it after installs, before CMD.
HEALTHCHECKTells Docker (and Compose) whether the app is actually alive.

CMD vs ENTRYPOINT, and exec vs shell form

# shell form: runs /bin/sh -c "..." (PID 1 is sh, signals can be missed)
CMD php artisan serve --host=0.0.0.0

# exec form: runs the binary directly (PID 1 is php, signals work)
CMD ["php", "artisan", "serve", "--host=0.0.0.0"]

# fixed binary + swappable args
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["php-fpm"]

Use exec form for anything that must receive SIGTERM and shut down cleanly — queue workers especially.

The two-minute Dockerfile review: Is the base pinned? Is the manifest copied before the source? Does it run as non-root? Is there a single obvious CMD? Is anything secret in ENV or ARG? If all five are yes, it is deployable.

Layers & Cache

Build speed is almost entirely about cache hits. Docker reuses a layer if its instruction and its input files are unchanged; the first miss invalidates everything below it.

Wrong order — every code edit re-installs dependencies
COPY . .                 # any file change busts the cache…
RUN npm ci              # …so this runs again, every single build
Right order — dependencies cached until the lockfile changes
COPY package.json package-lock.json ./
RUN npm ci
COPY . .                 # code churn stops here

Keep layers small

# bad: apt lists stay in the layer forever
RUN apt-get update
RUN apt-get install -y git
RUN rm -rf /var/lib/apt/lists/*

# good: one layer, cleaned before it is committed
RUN apt-get update \
 && apt-get install -y --no-install-recommends git \
 && rm -rf /var/lib/apt/lists/*

Forcing and sharing cache

CommandUse it when
docker build --no-cache -t app .A stale layer is hiding a bug
docker build --progress=plain .You need to see which step failed
docker buildx build --cache-to type=local,dest=.cache --cache-from type=local,src=.cache .CI builds that should reuse a cache across runs
docker builder pruneCache has grown to several GB
docker build --target build .Stop at a named stage to debug it
Order instructions by how often they change: OS packages, then language runtime, then dependency manifests, then your code. Stable at the top, churn at the bottom.

Multi-Stage Builds

Build with compilers and dev dependencies, then copy only the output into a clean runtime image. Same Dockerfile, one docker build.

PHP / Laravel — composer in a throwaway stage
# ---------- vendor stage ----------
FROM composer:2 AS vendor
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --prefer-dist --no-interaction

# ---------- runtime stage ----------
FROM php:8.4-fpm-alpine

RUN apk add --no-cache icu-dev oniguruma-dev libzip-dev \
 && docker-php-ext-install pdo_mysql intl mbstring zip opcache \
 && apk del icu-dev oniguruma-dev libzip-dev

WORKDIR /var/www/html
COPY . .
COPY --from=vendor /app/vendor ./vendor

RUN php artisan config:cache && php artisan route:cache \
 && chown -R www-data:www-data storage bootstrap/cache

USER www-data
EXPOSE 9000
CMD ["php-fpm"]

Why it is worth it

ImageSizeContains
Single-stage node:22~1.1 GBTypeScript, test tools, source, full OS toolchain
Multi-stage node:22-alpine~150–250 MBBuilt output and production dependencies only
PHP single-stage (composer image)~800 MBComposer, git, dev packages, caches
PHP multi-stage php:8.4-fpm-alpine~120 MBRuntime extensions and vendored code
Smaller images are not vanity: they pull faster in CI, start faster, and expose far fewer packages a scanner can flag. A distroless or Alpine runtime with no shell is a real security win.

.dockerignore

The build context is everything sent to the daemon. Without this file you ship node_modules, .git and your .env into it — slowly.

# dependency dirs are rebuilt inside the image

Check the size before you blame the network: docker build . prints "transferring context" in the first line. If that number is hundreds of MB, you forgot this file.

Docker Compose

One image is a demo; five services is an app. Compose declares the whole stack in one YAML file and starts it with one command.

compose.yaml — Laravel + MySQL + Redis + queue worker
services:
  app:
    build:
      context: .
      target: runtime
    # dev convenience: artisan serve. In production put nginx in
    # front of php-fpm and drop this command.
    command: ["php", "artisan", "serve", "--host=0.0.0.0", "--port=8000"]
    ports:
      - "8000:8000"
    environment:
      DB_HOST: db
      REDIS_HOST: cache
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    volumes:
      - "storage:/var/www/html/storage"

  queue:
    build: .
    command: ["php", "artisan", "queue:work", "--tries=3"]
    depends_on: [app, db, cache]
    restart: unless-stopped

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: app
      MYSQL_ROOT_PASSWORD: secret
    volumes:
      - "dbdata:/var/lib/mysql"
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-psecret"]
      interval: 5s
      retries: 10

  cache:
    image: redis:7-alpine
    volumes:
      - "redisdata:/data"

volumes:
  dbdata:
  redisdata:
  storage:
The commands
CommandWhat it does
docker compose up -d --buildBuild images, recreate what changed, run in background
docker compose psStatus and health of each service
docker compose logs -f appFollow one service's logs
docker compose exec app shShell into a running service
docker compose run --rm app php artisan migrateOne-off command in a throwaway container
docker compose downStop and remove containers (volumes survive)
docker compose down -v…and delete the volumes. Database gone.
docker compose watchSync code changes into the container live
docker compose configValidate and print the resolved YAML
Two habits that save an afternoon: use condition: service_healthy instead of a bare depends_on (Compose starts dependencies in order, it does not wait for the database to accept connections), and run one-off tasks with compose run --rm rather than polluting a long-lived container.

Volumes & Ports

Three kinds of mount

TypeExampleUse it for
Named volumedbdata:/var/lib/mysqlDatabases, uploads — anything Docker should own and back up
Bind mount./src:/app/srcLive code editing in development
tmpfstmpfs:/tmpCaches and scratch files that must never touch disk
 
# publish a port: HOST:CONTAINER
docker run -p 8080:80 nginx           # localhost:8080 → nginx:80
docker run -p 127.0.0.1:8080:80 nginx # bind to loopback only

# named volume
docker run -v dbdata:/var/lib/mysql mysql:8.4

# bind mount, read-only
docker run -v "$(pwd)/src:/app/src:ro" myapp

# inspect and clean
docker volume ls
docker volume inspect dbdata
docker volume prune
Windows note: bind mounts across the WSL boundary are slow. Keep source inside the Linux filesystem (\\wsl$\...) or use a named volume plus compose watch, and builds stop dragging.

Networks

Containers on the same user-defined network resolve each other by service name. That is why DB_HOST=db works and DB_HOST=localhost does not.

DriverBehaviourTypical use
bridgePrivate network, NAT to the host, DNS by nameDefault for Compose stacks
hostNo isolation — shares the host's portsPerformance-sensitive Linux services
noneLoopback onlyBatch jobs that need no network
overlaySpans multiple hostsSwarm / cluster mode
 
# create a network and put two containers on it
docker network create appnet
docker run -d --name db --network appnet mysql:8.4
docker run --rm --network appnet mysql:8.4 \
  mysql -h db -u root -psecret -e "SELECT 1"

# who is attached to what?
docker network inspect appnet

# from inside a container
docker exec -it app getent hosts db
docker exec -it app ping -c1 cache
EXPOSE is documentation; -p is publishing. Two containers on the same network reach each other on the container port without any -p at all. Publish only what the host (or the internet) must reach.

Config & Secrets

What belongs where
MechanismLivesSafe for secrets?
ENV in DockerfileBaked into the imageNo — visible in docker history
ARGBuild time onlyNo — also visible in history
-e / environment:Process environment at run timeBetter, but visible in inspect
env_file: / --env-fileA file on the host, injected at run timeYes, if the file stays out of git and the image
Docker secrets / cloud secret managerMounted as a file, encrypted at restYes — the right answer in production
 
# .env stays on the host and out of the image
docker run --env-file .env.production myapp:1.0

# build-time variable (not a secret)
docker build --build-arg APP_VERSION=1.4.2 -t myapp:1.4.2 .

# BuildKit secret: available only during the RUN, never in a layer
docker build --secret id=npmrc,src=$HOME/.npmrc .
# Dockerfile: RUN --mount=type=secret,id=npmrc npm ci
Once a secret is in a layer, deleting it later does not remove it. Rebuilding from RUN export TOKEN=... leaves the value recoverable in image history. Start with --env-file or a secret mount and you never have to rotate in a panic.

Never deploy :latest. Two servers pulling "latest" at different times can run different code while both claim the same version. Tag with a commit SHA or a semver, and keep latest as a convenience alias only.

# a hardened run
docker run -d --name app \
  --user 10001:10001 \
  --read-only --tmpfs /tmp \
  --memory 512m --cpus 1.5 \
  --cap-drop ALL --security-opt no-new-privileges \
  --restart unless-stopped \
  -p 127.0.0.1:8000:8000 \

  ghcr.io/acme/app:1.4.2
Enable BuildKit cache and a healthcheck before you need them. Most "Docker is slow" and "the container keeps restarting" tickets are a missing cache mount and a missing healthcheck, not the engine.

The five commands to run first

docker ps -a                     # did it die? exit code tells you why
docker logs --tail 200 NAME      # the actual error
docker inspect NAME              # mounts, env, network, exit code
docker exec -it NAME sh          # look from the inside
docker system df                 # where did the disk go
Exit code 137 means SIGKILL — almost always the OOM killer or docker stop timing out. Exit code 1 with no logs usually means the start command itself is wrong.

Interview Q&A

Image vs container?
An image is an immutable, layered template. A container is a running instance of that image with a thin writable layer on top. Many containers can run from one image; deleting a container never deletes the image.
How does layer caching work?
Each Dockerfile instruction produces a layer. Docker reuses a cached layer when the instruction and the checksum of its inputs are unchanged. The first cache miss invalidates every layer after it — which is why dependency manifests are copied before application code.
CMD vs ENTRYPOINT?
ENTRYPOINT sets the executable that always runs; CMD supplies default arguments that docker run IMAGE arg can override. Use both for CLI-style images, and prefer exec form (["php","fpm"]) so signals reach the process.
Why is my image 1 GB?
Usually one of: a full-language base image, a large build context (no .dockerignore), dev dependencies installed in the runtime stage, or apt-get lists left in an earlier layer. Multi-stage builds plus a slim/Alpine base plus cleaning in the same RUN line fixes it.
How do containers talk to each other?
Through a shared user-defined network. Docker's embedded DNS resolves the container or service name, so DB_HOST=db works. On the default bridge you only get IPs, which is why Compose creates a project network for you.
How do you handle secrets?
Never in ENV, ARG or a copied .env inside the image. Inject at run time with --env-file or an orchestrator secret, and use BuildKit --mount=type=secret for anything needed during a build. Rotate anything that was ever committed.
What is the difference between a bind mount and a volume?
A bind mount maps a host path into the container — great for live editing, tied to the host's layout. A named volume is managed by Docker in its own storage area — portable, faster on Windows/macOS, and the right choice for databases and uploads.
Container vs virtual machine?
A VM virtualises hardware and runs a full guest kernel; a container virtualises the OS and shares the host kernel using namespaces and cgroups. Containers start in under a second and are far denser, at the cost of weaker isolation.
How do you get zero-downtime deploys?
Run at least two replicas behind a load balancer, add a readiness check, then replace them one at a time (rolling) or swap a whole new stack in front of the old one (blue/green). Migrations must be backwards-compatible: add columns, deploy code, backfill, then remove old columns in a later release.
What does a container actually consist of?
A normal Linux process with namespaces (pid, net, mount, uts, ipc, user) for isolation, cgroups for resource limits, and a layered filesystem from the image. There is no guest kernel — the host kernel is shared.
