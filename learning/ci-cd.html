CI/CD

Every push tested, every merge shippable Pipelines GitHub Actions · GitLab CI zero-downtime deploys

Continuous Integration means every push is built and tested automatically. Continuous Delivery means a green pipeline always produces something deployable. Continuous Deployment means the deploy happens without a human. This guide builds the first two properly — real YAML for Laravel and Node, Docker image publishing, secrets done right, and the deployment patterns that keep a release from becoming an outage.

Cheap checks run first. Nothing expensive starts until the fast feedback is green.

The one rule that matters: if a step can be done by a human on a laptop, it can be done by the pipeline instead. The pipeline is the documentation of how to ship that is guaranteed not to be out of date.

What belongs in which stage

StageRuns onFails the build when…
LintEvery push, every PRStyle or static analysis complains
TestEvery push, every PRA test fails, or coverage drops below the floor
BuildMain, tags, releasesThe image or bundle cannot be produced

Build once, promote everywhere. The image tested in staging must be the exact image deployed to production — same digest. Rebuilding per environment means you are testing one thing and shipping another.

Your First Pipeline

Create .github/workflows/ci.yml in the repository. That is the whole setup — no server, no plugin.

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run lint
      - run: npm test
What each block is doing
BlockWhy it is there
onTests pull requests and main, so the badge means something
permissionsLeast privilege; the default token is too broad
concurrencyA new push cancels the previous run — saves minutes and confusion
timeout-minutesA hung job cannot burn an hour of quota
setup-node cache: npmCaches ~/.npm keyed on the lockfile
npm ciReproducible install from the lockfile; never npm install in CI
Debug ladder: read the failing step name, expand the log at the first error rather than the last, then reproduce locally with the same command. Nine out of ten red builds are a missing environment variable or a version that differs from your laptop.

GitHub Actions: the Parts You Will Use

Triggers

on:
  push:
    branches: [main]
    tags: ["v*"]        # release tags
    paths: ["src/**", "package.json"]   # skip doc-only changes
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 3 * * 1"   # Mondays 03:00 UTC
  workflow_dispatch:          # a manual Run button
  release:
    types: [published]

Jobs, needs and matrix

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: composer install --no-interaction --prefer-dist
      - run: vendor/bin/pint --test

  test:
    needs: lint                 # do not spend money if style fails
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        php: ["8.3", "8.4"]
        laravel: ["12.*", "13.*"]
    name: PHP ${{ matrix.php }} / Laravel ${{ matrix.laravel }}
    steps:
      - uses: actions/checkout@v4
      - run: echo "testing on ${{ matrix.php }}"

Reusable pieces: actions, artifacts, outputs

      # files between jobs
      - uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/
          retention-days: 7

      # a job that reads another job's output (e.g. the image tag)
      - id: meta
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
    # later job:
    needs: build
    steps:
      - run: echo "deploying ${{ needs.build.outputs.tag }}"
Two environment files, easily confused: $GITHUB_ENV sets variables for later steps; $GITHUB_OUTPUT passes values to other jobs. Writing echo "FOO=bar" into the log does neither.

A Complete Laravel Pipeline

Setup PHP with the right extensions, cache Composer, run migrations against a real MySQL, test, then build the image once.

name: Laravel CI

on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

concurrency:
  group: laravel-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15

    services:
      mysql:
        image: mysql:8.4
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: testing
        ports: ["3306:3306"]
        options: >- --health-cmd="mysqladmin ping -proot" --health-interval=5s --health-retries=15
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]

    env:
      DB_CONNECTION: mysql
      DB_HOST: 127.0.0.1
      DB_PORT: 3306
      DB_DATABASE: testing
      DB_USERNAME: root
      DB_PASSWORD: root
      CACHE_STORE: redis
      REDIS_HOST: 127.0.0.1

    steps:
      - uses: actions/checkout@v4

      - uses: shivammathur/setup-php@v2
        with:
          php-version: "8.4"
          extensions: mbstring, pdo_mysql, intl, zip, bcmath
          coverage: none
          tools: composer

      - name: Cache Composer
        uses: actions/cache@v4
        with:
          path: ~/.composer/cache
          key: composer-${{ hashFiles('**/composer.lock') }}
          restore-keys: composer-

      - name: Install
        run: composer install --no-interaction --prefer-dist --no-progress

      - name: Prepare
        run: |
          cp .env.example .env
          php artisan key:generate
          php artisan migrate --force

      - name: Style
        run: vendor/bin/pint --test

      - name: Tests
        run: php artisan test --parallel --coverage --min=80
Test the database you deploy on. SQLite hides json path behaviour, foreign-key timing and deadlocks. A MySQL service container costs about 20 seconds and removes an entire class of "works in CI, fails in production".

PHP 8.4 and Laravel 12/13 are current lines in 2026. Pin exact versions in the matrix if your composer constraints are narrow; a moving latest in CI is the same trap as a moving latest in Docker.

A Node / React Pipeline

name: Frontend CI

on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci

      - name: Types
        run: npx tsc --noEmit

      - name: Lint
        run: npm run lint

      - name: Unit tests
        run: npm test -- --run --coverage

      - name: Production build
        run: npm run build
        env:
          VITE_API_URL: https://api.example.com

      - name: E2E
        run: npx playwright test
        env:
          PLAYWRIGHT_BROWSERS_PATH: 0
Frontend env vars are baked at build time. VITE_*, NEXT_PUBLIC_* and React's REACT_APP_* values end up in the JavaScript bundle. Never put an API secret there — only the public base URL and, at most, a public key.

Build & Push a Docker Image

name: Release

on:
  push:
    tags: ["v*"]

permissions:
  contents: read
  packages: write        # push to ghcr.io

jobs:
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=sha,prefix=sha-

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          platforms: linux/amd64,linux/arm64
          provenance: true
What the cache lines actually save
SettingEffect
cache-from: type=ghaPulls layer cache from previous runs
cache-to: type=gha,mode=maxStores every layer, not just the final one
platforms: amd64 + arm64One tag that runs on both servers and Apple laptops
provenance: trueRecords how and from what the image was built
Do not build the image twice. Build here, use the digest downstream (${{ steps.build.outputs.digest }}) and deploy exactly that. The staging and production containers then cannot drift.

Repo secretsTokens available to all workflowsAny workflow edit can read them
Environment secretsProduction only, behind required reviewersLower — approval gates apply
GITHUB_TOKENRepo-scoped, expires with the jobLow — set permissions: tightly
OIDC → cloud roleShort-lived AWS/GCP/Azure credentialsLowest — nothing long-lived to leak
Hashed into the repoNothing. Ever.Certain incident
 
# repository → Settings → Environments → production → required reviewers
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com
    permissions:
      id-token: write      # OIDC, no stored cloud keys
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gh-deploy
          aws-region: eu-west-1
Pull requests from forks do not get your secrets. That is a feature. If a workflow needs secrets on pull_request, use pull_request_target only with extreme care — it runs untrusted code with your credentials. Prefer splitting into "test with no secrets" and "deploy on merge".

Deploy Strategies

StrategyHow it worksCost / risk
RecreateStop old, start newSimple, visible downtime
RollingReplace instances a few at a timeNo downtime; two versions briefly coexist
Blue / greenStand up the new stack, flip trafficDouble resources; instant rollback
CanarySend 5% of traffic, watch error rate, widenBest blast-radius control, needs metrics
Feature flagDeploy dark, enable per user or percentageDecouples deploy from release

Why two versions coexisting changes your code

During a rolling deploy, old and new code run at the same time against one database. Anything that is not backwards-compatible is an outage, not a deploy.

ChangeSafe during a rolling deploy?
Add a nullable columnYes
Rename a columnNo — old code still writes to the old name
Drop a columnOnly after no running code reads it
Add a required column without defaultNo — old code inserts break
Change a queue job payload shapeOnly if workers tolerate both shapes
Cache key format changeYes, with a version prefix (v2:)
Write your rollback before your deploy. A deploy job without a documented "how do we go back" line is only half a pipeline. Blue/green gives it to you for free: flip the router.

Safe Migrations in a Pipeline

Migrations are the step that most often turns a green deploy into a 3 a.m. incident, because they are the only irreversible thing in it.

Expand → migrate → contract, in three releases
# Release 1 — expand (schema only)
Schema::table('orders', function (Blueprint $t) {
    $t->string('status_v2')->nullable()->after('status');
});

# Release 2 — code writes both, reads the new one, backfill in batches
# Release 3 — contract: drop the old column once nothing reads it
# run migrations as a separate job, not from every web container
- name: Migrate
  run: php artisan migrate --force --isolated
  env:
    DB_HOST: ${{ secrets.DB_HOST }}
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
Rules that prevent the classic outage
  • Run migrations once per release — --isolated uses a lock so parallel containers cannot race.
  • Never run a long ALTER on a large table without a plan; it locks writes.
  • Take a backup (or a snapshot) before destructive migrations, and say so in the release notes.
  • Migrations must not depend on application code that may still be the old version.
  • Seed data belongs in a seeder, not in a migration that runs on production.

# .gitlab-ci.yml
stages: [test, build, deploy]

default:
  image: php:8.4-cli
  cache:
    key:
      files: [composer.lock]
    paths: [vendor/]

test:
  stage: test
  script:
    - composer install --no-interaction --prefer-dist
    - cp .env.example .env
    - php artisan key:generate
    - php artisan test

build:
  stage: build
  image: docker:28
  services: [docker:28-dind]
  script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  when: manual

Security jobs worth adding on day one

- uses: actions/dependency-review-action@v4
  with:
    fail-on-severity: high

# 2. static analysis for your language
- uses: github/codeql-action/analyze@v3
  with: { languages: javascript-typescript }

# 3. container scan before the push is promoted
- uses: aquasecurity/trivy-action@0.28.0
  with:
    image-ref: ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
    exit-code: "1"
    severity: CRITICAL,HIGH
    ignore-unfixed: true

# 4. keep dependencies moving
# .github/dependabot.yml handles composer, npm and actions weekly
Never scan with exit-code: 0 and call it security. A scanner that cannot fail the build is a dashboard. Start by failing on critical only, fix the backlog, then tighten.

Reproduce before you re-run. "Re-run failed jobs" hides the problem. Run the failing command in the same container image locally — docker run --rm -it -v "$PWD:/app" -w /app php:8.4-cli bash — and you will usually see the real error in one attempt.

Interview Q&A

What is the difference between CI, CD and CD?
Continuous Integration: every push is built and tested. Continuous Delivery: every green build is deployable, but a human decides. Continuous Deployment: the green build deploys itself. The two CDs differ only in who presses the button.
How do you keep a pipeline fast?
Cache dependencies and Docker layers, parallelise independent jobs, skip jobs by path filter, run cheap checks before expensive ones, keep the test suite honest (delete or fix slow flaky tests), and only reach for bigger runners after that. Target under ten minutes.
How do you handle secrets?
Short-lived, scoped, and never in the repo or logs. Prefer OIDC federation to a cloud role over stored keys, use environment-scoped secrets with required reviewers for production, and mask values. Rotate immediately if a secret ever reaches a log or an image layer.
Why build once and promote?
Rebuilding per environment means the artifact tested is not the artifact shipped — different base image digest, different dependency resolution. Build one immutable image, tag it with the commit SHA, and deploy that digest to staging and production.
How do you deploy without downtime?
At least two replicas, a readiness check, then rolling replacement or blue/green with instant traffic switching. The hard part is database compatibility: expand/contract migrations so old and new code can run side by side.
A migration broke production. What now?
Roll back the deploy to the previous image first (blue/green or a pinned tag), stop any further steps, then decide whether the schema change must be reversed or made backwards-compatible. Incident review afterwards should end with a migration rule, not a blame assignment.
How do you test a pipeline change?
Run it on a branch with workflow_dispatch or a PR trigger, use a staging environment that mirrors production, and keep an idempotent deploy script. Treat the pipeline as code: review it, version it, and test it before it touches production.
What is GitOps?
The desired state of the infrastructure lives in a Git repository; a controller (Argo CD, Flux) continuously reconciles the cluster to match. The deploy becomes a reviewed pull request, and drift is corrected automatically. The pipeline still builds and tests — GitOps takes over the delivery half.
How do you handle database tests in CI?
Run the real engine as a service container or a Docker Compose dependency, migrate a fresh database per job, and wrap each test in a transaction where the framework supports it. SQLite is fine for fast unit tests, but at least one job must run against MySQL/PostgreSQL.
What do you monitor after a deploy?
Error rate, latency percentiles, queue depth, failed jobs and a business metric (signups, orders). Automate a canary check and roll back on a threshold instead of waiting for a support ticket.
