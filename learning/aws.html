Amazon Web Services

The cloud, explained service by service AWS since 2006 · us-east-1 first 39 regions · 124 AZs

AWS is a warehouse of rented computers: you ask for a server, a bucket, a database or a queue through an API call, and you pay for what you use by the second. This guide walks the services that actually show up in projects and interviews, with the CLI commands to run them, the pricing traps that surprise beginners, and a first architecture you can build in a day.

What AWS Actually Is

Before any service name: the mental model. You stopped buying computers and started renting them, by the minute, from a company that owns millions.

The one habit that makes AWS click: everything in AWS is an API call. Clicking Launch instance in the console sends the same request you could type as aws ec2 run-instances. Learn the words — create, describe, list, delete — and every service suddenly speaks the same grammar.

The golden rule: run across at least two Availability Zones. One AZ failing is a normal, expected event — an unhealthy disk, a network cut, a power incident. Two copies means your app keeps running; a single AZ means you are renting a server with extra steps. Note that an AZ can also be constrained: AWS may stop new accounts from using it, so code with AZ IDs, not hard-coded a/b/c letters.

Choosing where to deploy

QuestionWhy it decides

Where must the data live?GDPR, RBI, data-residency rules pin storage to a country or region
What does it cost?The same instance can be ~30% cheaper in another region
Which services exist there?New services launch in a few regions first; some never reach all of them
Disaster recovery?Two regions for real DR, two AZs for everyday resilience — they are not the same thing

Pricing & the Free Tier

You pay for usage, per second, with no contract. That sounds safe — until a forgotten resource quietly bills you all month.

Three ways to pay for the same machine

OptionDiscountUse it when
On-DemandNone — the base priceUnknown workloads, first experiments, spiky traffic
Savings Plans / ReservedUp to ~72% for a 1–3 year commitmentA server you already know runs 24/7

What "free" currently means

New accounts (since 15 July 2025)

AWS replaced the classic 12-month free tier with a credit-based Free plan: up to $200 in credits over 6 months — $100 at sign-up, $100 more as you explore — then the account closes unless you move to the paid plan. Older accounts keep their 12-month benefits (750 hrs of t3.micro, 5 GB S3, 750 hrs of RDS).

Where beginners get the bill

TrapHow to avoid it

Day-one guardrail: open Billing → Budgets and create a budget alarm at $5. It takes ninety seconds and is the cheapest insurance AWS sells. Then check the AWS Pricing Calculator before building anything big.

EC2 in one screen

Launch and connect — the whole ritual
# 1. Identity check - always works, proves your credentials
aws sts get-caller-identity

# 2. Launch a free-tier friendly instance in your default VPC
aws ec2 run-instances \
  --image-id ami-0c02fb55956c7d316 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-0abcdef1234567890 \
  --subnet-id subnet-0abcdef1234567890 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=first-server}]'

# 3. Watch it boot, grab its public address
aws ec2 describe-instances \
  --filters "Name=instance-state-name,Values=running" \
  --query "Reservations[].Instances[].[InstanceId,PublicIpAddress]" \
  --output table

# 4. When you are done - this is the button people forget
aws ec2 terminate-instances --instance-ids i-0123456789abcdef0
Three words you need before launching
AMI — the blueprint: OS plus whatever image you chose. Ubuntu, Amazon Linux, or your baked custom image.
Instance type — the size. t3.micro = 1 vCPU / 1 GB; t3.large = 2 vCPU / 8 GB. The t family bursts above its baseline.
Key pair — the SSH key. Lose it and you log in via the console, not via magic.

Lambda: code without a server

A complete function (Python runtime)
import json
import os
import urllib.request

def lambda_handler(event, context):
    """Runs only while a request is in flight - then freezes."""
    city = event.get("queryStringParameters", {}).get("city", "Tokyo")
    url = f"https://api.weather.example/v1/{city.lower()}"

    with urllib.request.urlopen(url, timeout=3) as r:
        data = json.loads(r.read().decode())

    return {
        "statusCode": 200,
        "headers": {"content-type": "application/json"},
        "body": json.dumps({"city": city, "temp": data["temp_c"],
                           "env": os.environ.get("STAGE", "dev")}),
    }
Lambda factNumber
Max execution time15 minutes — anything longer belongs on ECS or EC2
Memory range128 MB to 10,240 MB — CPU scales with memory
BillingPer millisecond, per GB — a cold API call costs a fraction of a cent
Cold startFirst invocation after idle takes hundreds of ms — provisioned concurrency trades money for consistency
Free allowance1M requests and 400,000 GB-seconds, every month, forever
Decision in one line: need SSH or special software → EC2. Need a container platform → Fargate. Need to react to an event in under a second and never want to patch → Lambda.

Storage — S3, EBS and EFS

Three storage services, three completely different jobs. Picking the wrong one is the most common early mistake.

ServiceWhat it isReach for it when
Amazon S3Object storage: files (objects) inside buckets, reached over HTTPUploads, backups, static websites, images, logs — the default answer
Amazon EBSA block disk you attach to one instance, like an external driveThe root disk of an EC2 box or a database's data volume
Amazon EFSA shared network file system, mountable by many machines at onceContent shared between several servers or containers
S3 GlacierDeep archive inside S3, retrieval takes minutes to hoursCompliance archives you expect never to read

Everyday S3 commands
# Bucket names are global and permanent - pick something unique
aws s3 mb s3://my-first-bucket-2026 --region ap-south-1

# Copy files up and down
aws s3 cp ./dist/index.html s3://my-first-bucket-2026/index.html
aws s3 cp s3://my-first-bucket-2026/logo.png ./logo.png

# The workhorse: mirror a whole folder, only changed files
aws s3 sync ./dist s3://my-first-bucket-2026 --delete

aws s3 ls s3://my-first-bucket-2026 --recursive --human-readable
aws s3 rb s3://my-first-bucket-2026 --force   # delete only when empty
Defaults worth turning on: versioning (recover from a bad upload), block public access (nobody reads your bucket by accident), and server-side encryption. S3 promises "eleven nines" of durability per object — durability is not permission, and it is certainly not a backup of deleted files without versioning.

Databases

AWS offers a database for every shape of data. Choose by shape first, brand second.

ServiceShape & speedTypical job

Amazon AuroraRelational, MySQL/PostgreSQL compatibleRDS with better performance and up to 15 read replicas

Amazon ElastiCacheRedis or Memcached, in memoryCache and hot sessions in front of a slower database

Multi-AZ vs Read Replicas — the interview pair

FeatureWhat it doesWhat it does not do
Multi-AZSynchronous standby in a second AZ; DNS flips to it automatically on failureDoes not make reads faster — you never write to it yourself
Read replicaAsynchronous copy you can read from; scale reads, or keep one for reportingDoes not fail over on its own — promote it yourself during a disaster
Working with both from the CLI
# Relational: your databases, one command away
aws rds describe-db-instances \
  --query "DBInstances[].[DBInstanceIdentifier,DBInstanceStatus,DBInstanceClass]" \
  --output table

# Serverless key-value: list, then put and read
aws dynamodb list-tables
aws dynamodb put-item --table-name orders \
  --item '{"id": {"S": "o-1001"}, "total": {"N": "42.50"}, "status": {"S": "paid"}}'
aws dynamodb query --table-name orders \
  --key-condition-expression "id = :id" --expression-attribute-values '{":id": {"S": "o-1001"}}'
Rule of thumb: data with relationships and transactions → RDS or Aurora. Flat records read and written by primary key → DynamoDB. Same answer repeated thousands of times per second → put a ElastiCache cache in front. Starting with DynamoDB because "serverless" and then needing joins is the most expensive lesson in this table.

IAM is the front door of your AWS account. Get it right before you launch anything, because every credential you mint can spend your money.

A least-privilege policy, annotated
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListAndReadOnOneBucket",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-first-bucket-2026",
        "arn:aws:s3:::my-first-bucket-2026/*"
      ]
    },
    {
      "Sid": "DenyEverythingElseIsImplicit",
      "Effect": "Deny",
      "Action": "s3:DeleteBucket",
      "Resource": "arn:aws:s3:::my-first-bucket-2026",
      "Condition": { "StringNotEquals": { "aws:PrincipalTag/team": "platform" } }
    }
  ]
}
Habits that prevent almost every AWS breach story
1. MFA everywhere — root and every IAM user. A stolen password without a second factor is just a typo.
2. Roles over keys — EC2, Lambda and ECS get credentials from an instance or task role. Static access keys in a repo are a classic leak.
3. No * actions — "Action": "*" on "Resource": "*" is an accident waiting for a bad day.
4. Audit yourself — enable CloudTrail (who called what) and IAM Access Analyzer (which policies opened outward).
5. Encrypt by default — S3, EBS and RDS all offer encryption at rest; KMS keys are auditable.
6. Understand the split — AWS secures of the cloud; you secure in it: your keys, your buckets, your patches.

Messaging & Events

Two services do most of the work: a queue you pull from, and a topic you broadcast to. Once those click, the rest is decoration.

SQS detailWhy it matters
Visibility timeoutA message being handled disappears for others, then reappears if the worker dies
Dead-letter queueMessages that keep failing park here so you can read them instead of losing them
FIFO queuesExactly-once, ordered delivery — at the cost of throughput
Standard queuesAt-least-once, nearly unlimited throughput — make consumers idempotent
Why bother? Queues turn one fragile request into two survivable ones. When your search index is down, orders still succeed and the indexer catches up later — that is availability bought with a service that costs $0.40 per million messages.

An alarm you should create today
# Alarm on 5xx errors from your load balancer, then read it
aws cloudwatch put-alarm-alarm --alarm-name alb-5xx-high \
  --metric-name TargetResponseCodeCount --namespace AWS/ApplicationELB \
  --statistic Sum --period 60 --threshold 5 \
  --comparison-operator GreaterThanThreshold --evaluation-periods 1 \
  --alarm-actions arn:aws:sns:ap-south-1:111122223333:ops-topic

aws cloudwatch describe-alarms --state-value ALARM --output table
aws logs tail /aws/lambda/order-api --follow

Your First 24 Hours on AWS

A real sequence, in order. By the end you will have used IAM, S3, CloudFront, Lambda, API Gateway, DynamoDB and CloudWatch — and spent close to nothing.

Step 1 — Account and guardrails (20 min)
  1. Create the account, confirm the email, add a credit card.
  2. Enable MFA on the root user — an app on your phone, not SMS.
  3. Create the $5 budget alarm in the Billing console.
  4. Create an IAM user for yourself with a group policy, and leave root alone.
Step 2 — Static website on S3 + CloudFront (45 min)
aws s3 mb s3://my-first-bucket-2026 --region ap-south-1
aws s3 website s3://my-first-bucket-2026 --index-document index.html
aws s3 cp ./index.html s3://my-first-bucket-2026/index.html

# Then, in the console: create a CloudFront distribution with that bucket
# as origin, and note the domain name it hands you.
# https://d111111abcdef8.cloudfront.net is now your live website.
Step 3 — A serverless API (90 min)
  1. Create a DynamoDB table notes with partition key id.
  2. Create a Lambda function, paste a handler, and give it a role that can write to that one table.
  3. Create an API Gateway HTTP API with a GET /notes route pointing at the function.
  4. Call the URL with curl. When JSON comes back, you just ran a full request through four services.
Step 4 — See the whole picture

                    |                 |

Step 5 — Tear it down (15 min, do not skip)
# Delete in reverse order of creation
aws cloudfront disable-distribution --id E1EXAMPLE   # must disable before delete
aws lambda delete-function --function-name notes-api
aws apigatewayv2 delete-api --api-id abc123
aws dynamodb delete-table --table-name notes

aws ec2 describe-instances --filters "Name=instance-state-name,Values=running" --output table
Expected cost for this project: well under a dollar. CloudFront, Lambda, API Gateway and DynamoDB all sit inside free allowances, and the S3 bucket holds a few kilobytes. The bill arrives only from things you forget to delete — which is why step 5 is part of the project, not cleanup after it.

Interview Q&A

The questions that come up again and again, answered the way a candidate should say them aloud.

What is the difference between a Region and an Availability Zone?
A Region is a geographic area (for example ap-south-1, Mumbai) and everything in it stays inside it. An AZ is one or more data centres inside that region with independent power and cooling — ap-south-1a. Each region has at least three AZs, connected by low-latency fibre, so I spread the app across two or more of them to survive losing one.
S3, EBS or EFS — which do you choose?
S3 for objects over HTTP: uploads, backups, static assets. EBS for a disk attached to one instance, like a root volume or a database volume. EFS when several machines must mount the same files. I pick S3 unless something specifically needs a block device or a POSIX file system.
Security group vs NACL?
A security group is attached to an instance, stateful, allow-only, and it lets replies back automatically. A NACL is attached to a subnet, stateless, and can deny traffic explicitly — you must allow the return path yourself. In practice I set a tight security group and leave the NACL at its defaults unless I need to block a range.
When would you use an IAM role instead of an access key?
Always, when something runs on AWS. An EC2 instance, Lambda function or ECS task assumes a role automatically — no keys on disk, no rotation, no leak through a repository. Static access keys are for humans and CI outside AWS, and even then I scope them to a policy and rotate them.
EC2 or Lambda?
EC2 when I need long-running processes, SSH, GPUs, special runtimes or anything past 15 minutes. Lambda when work is event-driven, bursty or idle most of the day — it scales per request and costs a fraction of a cent per call. Many real systems use both: Lambda for webhooks, a small ECS or EC2 fleet for the heavy lifting.
Multi-AZ or read replica — what is each for?
Multi-AZ is for availability: a synchronous standby in another AZ that DNS fails over to automatically. Read replicas are for scale: asynchronous copies that serve reads, or that you promote manually in a disaster. A production database usually wants Multi-AZ plus one or two replicas.
SQS, SNS or EventBridge?
SQS is a queue one consumer pulls from — ideal for decoupling a slow step. SNS is a topic that pushes one message to many subscribers — alerts and fan-out. EventBridge is an event bus with filtering and schedules, connecting AWS services, SaaS vendors and cron rules. My common pattern is SNS fan-out into per-consumer SQS queues.
How do you make an application highly available?
Put the stateless part — web and app tier — in private subnets across two or more AZs behind an Application Load Balancer with health checks. Put the database in Multi-AZ with backups and a defined RPO/RTO. Cache at the edge with CloudFront, make every consumer idempotent, and test a failure deliberately rather than waiting for one.
What is the shared responsibility model?
AWS is responsible for security of the cloud: the buildings, hardware, hypervisor and managed service internals. I am responsible for security in the cloud: my IAM policies, my data, my OS patches on EC2, my encryption settings and my network rules. Misunderstanding that split is behind most real incidents.
How would you cut an AWS bill in half?
First, delete: idle instances, unattached volumes, old snapshots, forgotten load balancers. Second, right-size from CloudWatch data instead of guessing. Third, commit on stable workloads with Savings Plans, and move fault-tolerant batch work to Spot. Fourth, move cacheable traffic to CloudFront to cut data-transfer fees. Then set a budget alarm so it never creeps back.
What is the Well-Architected Framework?
AWS's checklist of six pillars: operational excellence, security, reliability, performance efficiency, cost optimization and sustainability. I use it as a review lens before launch: is this observable, least-privilege, recoverable, right-sized, affordable and not wasting energy?
Your S3 bucket holds backups. Is that a disaster-recovery plan?
No. A single bucket in one region is a copy, not a plan. I would enable versioning, add cross-region replication to a second account, and define an RPO and RTO in writing. Then I restore from the replica once, on purpose, to prove it works.
