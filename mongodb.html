What is MongoDB?

MongoDB is an open-source NoSQL document database (released 2009). Instead of rows and columns it stores flexible BSON documents â€” JSON-like binary structures â€” inside collections. One database holds many collections; one collection holds many documents.

Document Model

Data is stored as JSON-like documents that map naturally to objects in code.

Flexible Schema

Documents in one collection can differ in fields â€” evolve without migrations.

Horizontal Scaling

Built-in replication (replica sets) and sharding for scale-out growth.

SQL vs MongoDB terminology concept

When to choose MongoDB — rapidly evolving schemas, nested / hierarchical data (product catalogs, user profiles, CMS content), high write throughput, and horizontal scale-out needs. For heavily relational data with multi-table transactions and strict integrity, a relational DB (PostgreSQL / MySQL) is usually the better fit.

// Switch (or lazily create) a database
use shopdb

// Collections are created on first insert â€” no CREATE TABLE step

// Inspect what exists
db                                    // current database
show dbs                             // list databases
show collections                     // list collections
db.products.countDocuments()          // count docs
db.getCollectionNames()               // array of names
Databases are lazy. use shopdb does not create anything on disk until the first document is inserted. Same for collections â€” db.products.insertOne({...}) creates the collection automatically.

CRUD Operations

Create, Read, Update and Delete documents â€” the verbs you will use every day.

Create

insertOne / insertMany mongosh
// Single document â€” _id (ObjectId) is auto-generated if omitted
db.products.insertOne({
  name: "Mechanical Keyboard",
  price: 2499,
  tags: ["hardware", "keyboard"],
  stock: 42,
  createdAt: new Date()
})

// Many documents at once
db.products.insertMany([
  { name: "USB-C Hub", price: 899, tags: [accessories] },
  { name: "Webcam 1080p", price: 1599, tags: [video] },
  { name: "Desk Mat", price: 499, tags: [accessories] }
])

Read

find, findOne, projection, sort/skip/limit mongosh
// All documents
db.products.find()

// Filter + projection (1 = include, 0 = exclude; _id included by default)
db.products.find(
  { price: { $lte: 1000 } },
  { name: 1, price: 1, _id: 0 }
)

// First match only
db.products.findOne({ name: "USB-C Hub" })

// Sort desc by price, skip 5, take 10 â€” pagination
db.products.find().sort({ price: -1 }).skip(5).limit(10)

// Count
db.products.countDocuments({ stock: { $gt: 0 } })

Update

updateOne / updateMany / upsert mongosh
// Update first match
db.products.updateOne(
  { name: "USB-C Hub" },
  { $set: { price: 999 }, $inc: { stock: -1 } }
)

// Update ALL matches
db.products.updateMany(
  { tags: "accessories" },
  { $set: { discounted: true } }
)

// Upsert â€” update if exists, insert if not
db.products.updateOne(
  { sku: "KB-001" },
  { $set: { name: "Keyboard Pro", price: 3499 } },
  { upsert: true }
)

// replaceOne swaps the whole document (except _id)
db.products.replaceOne({ sku: "KB-001" }, { name: "New", price: 1 })

Delete

deleteOne / deleteMany mongosh
db.products.deleteOne({ sku: "KB-001" })

// Remove everything matching (no filter = remove ALL documents!)
db.products.deleteMany({ stock: 0 })

// Drop the whole collection including its indexes
db.products.drop()

Query Operators

Operators are the $-prefixed keys that make queries expressive.

OperatorDescription
$set / $unsetSet a field's value / remove the field

Nested fields use dot notation: { "address.city": "Jaipur" } matches the city field inside the embedded address document, and { "scores.math": { $gte: 80 } } reaches into arrays of sub-documents too.

Schema Design

"Flexible schema" does not mean "no schema". Design documents around the queries your app runs.

Embedding vs Referencing decision
AspectEmbed (sub-document / array)Reference (_id link)
ReadsOne query â€” data ships togetherNeeds extra query / $lookup
Best forOne-to-FEW (order items, address, comments on a post)One-to-MANY / MANY-to-MANY (products & categories)

Common patterns mongosh
// Pattern 1 â€” Embed one-to-few: order with line items
{
  _id: ObjectId("..."),
  customer: "Aarti",
  items: [
    { sku: "KB-001", qty: 1, price: 3499 },
    { sku: "HUB-02", qty: 2, price: 999 }
  ],
  total: 5497
}

// Pattern 2 â€” Reference one-to-many: product points to category
{ _id: ObjectId("...A"), name: "USB-C Hub", categoryId: ObjectId("...B") }

// Pattern 3 â€” Extended reference: copy often-needed fields to avoid lookups
{ name: "USB-C Hub", categoryId: ObjectId("...B"), categoryName: "Accessories" }

    }
  },

Indexing

Without an index every query scans the whole collection (COLLSCAN). Indexes turn that into an index walk (IXSCAN) â€” the single biggest performance lever in MongoDB.

Index types mongosh
// Single field
db.products.createIndex({ price: 1 })              // 1 asc, -1 desc

// Compound â€” order matters! Follows ESR rule
db.products.createIndex({ category: 1, price: -1 })
// Unique index
db.users.createIndex({ email: 1 }, { unique: true })
// Text index for search
db.articles.createIndex({ title: "text", body: "text" })
// TTL index â€” auto-delete after 3600s from createdAt
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
// Partial index â€” smaller, only covers hot subset
db.orders.createIndex(
  { createdAt: 1 },
  { partialFilterExpression: { status: "pending" } }
)

db.products.getIndexes()                            // list
db.products.dropIndex("price_1")                    // drop
db.products.explain("executionStats").find({ price: 999 })
The ESR rule for compound indexes — order fields as Equality first, then Sort, then Range. For find({ category: "x" }).sort({ createdAt: -1 }).where(price > 100) build { category: 1, createdAt: -1, price: 1 }.
Reading explain() checklist
  • winningPlan.stage â€” want IXSCAN; avoid COLLSCAN.
  • totalKeysExamined ≈ nReturned â€” index is selective.
  • totalDocsExamined much larger than nReturned → fetch overhead; consider a covered query (projection uses only indexed fields).
  • SORT stage in plan → in-memory sort; add the sort fields to the index.

Aggregation Pipeline

The aggregation framework processes documents through a pipeline of stages â€” MongoDB's answer to GROUP BY, joins, and ETL-style transformations.

Core stages reference
StagePurpose
$matchFilter documents (like find) â€” put early to use indexes
$groupGroup by key, compute $sum / $avg / $min / $max / $count
$projectReshape: keep/rename/compute fields
$sort / $limit / $skipOrder and paginate
$lookupLeft outer join with another collection
$unwindDeconstruct an array into one doc per element
$addFields / $setAdd computed fields without dropping others
$facetRun multiple sub-pipelines on the same input (faceted search)
$out / $mergeWrite results to a collection
Revenue per category (match → group → sort) pipeline
db.orders.aggregate([
  { $match:  { status: "paid", createdAt: { $gte: new Date("2026-01-01") } } },
  { $unwind: "$items" },
  { $group: {
      _id: "$items.category",
      revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } },
      orders:  { $sum: 1 },
      avgQty:  { $avg: "$items.qty" }
  }},
  { $sort: { revenue: -1 } },
  { $limit: 10 }
])
Join with $lookup pipeline
db.products.aggregate([
  {
    $lookup: {
      from: "categories",          // foreign collection
      localField: "categoryId",     // field here
      foreignField: "_id",          // field there
      as: "category"                // output array field
    }
  },
  { $unwind: "$category" },         // flatten 1-element array
  { $project: { name: 1, price: 1, "category.name": 1 } }
])

Performance Tips

Habits that keep queries fast as data grows.

Index your filters and sorts. Verify with explain("executionStats") â€” no COLLSCANs on large collections.
Project only needed fields â€” less network I/O, enables covered queries.
Put $match and $limit early in pipelines so later stages process fewer documents.
Avoid unbounded embedded arrays â€” they bloat documents toward the 16 MB limit and invalidate on every write.
Use ObjectId-friendly pagination (_id > lastId) instead of deep skip() offsets.
Bulk writes with bulkWrite()/insertMany instead of loops of single ops.
Leading wildcards kill regex performance â€” /^abc/ can use an index, /abc/ cannot.

Replication & Transactions

Production deployments run a replica set: one PRIMARY accepts writes, SECONDARIES replicate via the oplog and can be elected primary on failure. Transactions (4.0+) give multi-document ACID.

Multi-document transaction mongosh
const session = db.getMongo().startSession()

try {
  session.startTransaction()

  const accounts = session.getDatabase("shopdb").accounts
  accounts.updateOne({ _id: "alice" }, { $inc: { balance: -500 } })
  accounts.updateOne({ _id: "bob"   }, { $inc: { balance:  500 } })

  session.commitTransaction()
} catch (e) {
  session.abortTransaction()
} finally {
  session.endSession()
}

SettingMeaning
w: 1Primary acknowledged â€” fastest, smallest durability guarantee
w: "majority"Majority of replica set acknowledged â€” survives failover safely
j: trueWrite is on disk journal before ack
readPreference primaryReads hit primary â€” always consistent
