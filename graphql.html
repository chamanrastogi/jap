Introduction

What is GraphQL?

GraphQL is a spec created by Facebook in 2015. The client sends a query describing the exact fields it wants; the server resolves them against a central schema and returns a JSON document in the same shape. No REST endpoint explosion, no fixed payloads.

Query

Fetch data. "Give me the post and its author's name."

Mutation

Change data. "Create this post, then return its id."

Subscription

Live updates over a websocket. "Tell me when a comment arrives."

GraphQL vs REST concept
ConcernRESTGraphQL
Data shapeFixed per endpointClient selects exact fields
Round tripsOften one per resourceOne for the whole tree
EndpointsMany (/posts, /posts/1, ...)One (/graphql)
Over / under fetchCommonAvoided by field selection
ContractScattered across endpointsCentral typed SDL schema
CachingHTTP cache friendlyNeeds APQ / persisted queries
Evolving the APINew endpoints, versioningAdd fields, deprecate old ones
When to choose GraphQL — multiple clients (web + mobile) needing different payloads, deeply nested data, or APIs that grow fast. For a simple CRUD backend consumed by one first-party web client, a small REST API is often the more boring (and better) choice.
Step 01 — Setup

Install Lighthouse

Lighthouse is the most popular GraphQL server for Laravel. It turns a graphql/schema.graphql file into a working endpoint with Eloquent-aware directives and zero controllers.

Installation bash
# 1. Install Lighthouse (works with Laravel 10 / 11 / 12 / 13)

composer require nuwave/lighthouse

# 2. Publish the config and the default schema

php artisan vendor:publish --tag=lighthouse-config

Step 02 — Schema

The Schema (SDL)

The schema lives in graphql/schema.graphql using the Schema Definition Language. It is the single contract between client and server. Every resolvable piece of data is a type; the entry points are the type Query and type Mutation roots.

graphql/schema.graphql graphql
type Query {
  posts: [Post!]!  @paginate
  post(id: ID!): Post @find
}

type Post {
  id: ID!
  title: String!
  body: String!
  published: Boolean!
  author: User! @belongsTo
  comments: [Comment!]! @hasMany
}

type User {
  id: ID!
  name: String!
  email: String! @hidden
  posts: [Post!]! @hasMany
}

type Comment {
  id: ID!
  body: String!
}
Scalar & Enum Types graphql
# Built-in scalars: Int, Float, String, Boolean, ID
# Lighthouse ships DateTime out of the box

scalar DateTime

enum PostStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}
Type System — at a glance
SymbolMeaning
String!Non-null string (always present)
[Post!]!Non-null list of non-null posts
[Post]List that may contain nulls

implements NodeInterface conformance

Nullability is a promise. email: String (nullable) tells clients to handle null; email: String! guarantees a value. Think about which one is true for your data before you type it.
Step 03 — Queries

Querying Data

A query selects fields in the exact shape you want returned. Queries can use arguments, aliases, fragments, and variables to stay reusable.

Aliases graphql
# Two queries in one round trip

query {
  latest: posts(first: 3) { title }
  featured: posts(first: 1) { title }
}
Fragments graphql
# Reuse a field set across queries

query Feed {
  posts(first: 10) {
    ...PostCard
  }
}

fragment PostCard on Post {
  title
  excerpt
  author { name }
}
Variables & Pagination graphql
query Posts($first: Int!, $page: Int) {
  posts(first: $first, page: $page) {
    data {
      id
      title
    }
    total
    per_page
  }
}

# Variables payload sent alongside the query:

{
  "first": 10,
  "page": 2
}

Step 04 — Resolvers

Resolvers

A resolver is the function that supplies the value for a field. Lighthouse resolves most fields for free: an Eloquent model attribute maps to a field of the same name, and relationship directives use the model's own relationship methods. Only write a resolver when the value is computed.

Computed Field — initials graphql
type User {
  id: ID!
  name: String!
  initials: String! @field(resolver: "App\\GraphQL\\Resolvers\\UserInitials")
}
app/GraphQL/Resolvers/UserInitials.php php
namespace App\GraphQL\Resolvers;

use App\Models\User;

class UserInitials
{
    public function __invoke(User $root): string
    {
        $parts = preg_split('/\s+/', trim($root->name));

        return strtoupper(
            ($parts[0][0] ?? '') .
            ($parts[1][0] ?? '')
        );
    }
}
Query with Arguments & Search graphql
type Query {
  searchPosts(search: String, first: Int): [Post!]!
    @field(resolver: "App\\GraphQL\\Queries\\SearchPosts")
}
app/GraphQL/Queries/SearchPosts.php php
namespace App\GraphQL\Queries;

use App\Models\Post;

class SearchPosts
{
    public function __invoke($root, array $args): array
    {
        return Post::query()
            ->when(
                $args['search'] ?? null,
                fn ($q, $s) => $q->where('title', 'like', "%{$s}%")
            )
            ->latest()
            ->take($args['first'] ?? 10)
            ->get()
            ->all();
    }
}
Keep business logic in classes. A resolver that only forwards to an Eloquent method or a dedicated service/action keeps the schema thin and the logic testable without touching GraphQL at all.
Step 05 — Mutations

Mutations

Mutations change data. They are declared on the type Mutation root. Lighthouse ships persistence directives (@create, @update, @upsert, @delete) that save you from writing most handlers, and @rules validates input using Laravel's validator.

graphql/schema.graphql graphql
type Mutation {
  createPost(input: CreatePostInput! @spread): Post! @create
  updatePost(id: ID!, input: UpdatePostInput! @spread): Post! @update
  deletePost(id: ID! @whereKey): Post @delete
}

input CreatePostInput {
  title: String! @rules(apply: ["required", "min:3", "max:255"])
  body: String! @rules(apply: ["required"])
  author_id: ID! @rules(apply: ["exists:users,id"])
}

input UpdatePostInput {
  title: String @rules(apply: ["min:3", "max:255"])
  body: String
}
Calling the Mutation graphql
mutation CreatePost {
  createPost(input: {
    title: "GraphQL is neat",
    body: "Ask for exactly the fields you need.",
    author_id: 1
  }) {
    id
    title
  }
}

# Response:

{
  "data": {
    "createPost": {
      "id": "1",
      "title": "GraphQL is neat"
    }
  }
}
Custom Mutation — Login graphql
extend type Mutation {
  login(email: String!, password: String!): User!
    @field(resolver: "App\\GraphQL\\Mutations\\Login")
}
app/GraphQL/Mutations/Login.php php
namespace App\GraphQL\Mutations;

use App\Models\User;
use Illuminate\Support\Facades\Hash;

class Login
{
    public function __invoke($root, array $args): User
    {
        $user = User::where('email', $args['email'])->first();

        if (! $user || ! Hash::check($args['password'], $user->password)) {
            throw new \RuntimeException('Invalid credentials.');
        }

        $user->plain_token = $user->createToken('graphql')->plainTextToken;

        return $user;
    }
}
Step 06 — Eloquent

Eloquent & the N+1 Problem

The classic pitfall: 100 posts × 1 author query = 101 database queries. Lighthouse's default relationship directives resolve relations in batches (its own BatchLoader), so a nested author or comments field does not trigger N+1. For custom resolvers, batch explicitly.

Counting & Eager Loading graphql
type Post {
  id: ID!
  title: String!
  commentsCount: Int! @withCount(relation: "comments")
  author: User! @belongsTo
  recentComments: [Comment!]! @hasMany(scopes: ["latest"])
}
Elastic Scopes for Queries graphql
type Query {
  publishedPosts: [Post!]!
    @paginate(scopes: ["published"])
}

# app/Models/Post.php

public function scopePublished($query): void
{
    $query->where('published', true);
}
Batching a Custom Resolver php
// Resolve "authorName" for a list of posts without N+1:
// Load the relation once per field, then index by key.

public function __invoke(Post $root): string
{
    $root->load('author');  // Lighthouse batches the belongsTo call

    return $root->author->name;
}
Watch for over-fetching too. A client asking for only id and title still lets Lighthouse build the query from the requested fields, so columns stay scoped to what was asked for.
Step 07 — Auth

Authentication & Security

Protect fields with @guard, resolve the current user with @auth, and authorize with policies via @can. Use Laravel Sanctum tokens for SPAs and mobile clients.

Protecting Fields graphql
extend type Query {
  me: User! @auth @guard(with: ["sanctum"])

  drafts: [Post!]!
    @guard
    @can(ability: "viewAny", model: "App\\Models\\Post")

  userPosts(id: ID!): [Post!]!
    @guard
    @can(ability: "view", find: "App\\Models\\User")
}
Sending the Token bash
# Issue a token in your login endpoint, then send it as a header

# Authorization: Bearer 1|abc123...
Production Hardening php
// config/lighthouse.php

'security' => [
    // Limit how deep a query tree can go
    'max_depth' => 10,

    // Limit total field count (blocks expensive queries)
    'max_complexity' => 100,

    // Hide the schema from clients in production
    'disable_introspection' => (bool) env('LIGHTHOUSE_DISABLE_INTROSPECTION', true),
],

Security checklist

Guard every mutation that writes data — an unguarded @create is an open door.
Scope relationships to the authenticated user (@whereAuth(guard: "sanctum")) instead of returning everything.
Mark internal columns with @hidden so they don't appear in introspection.
Set max_depth / max_complexity in production to stop abusive queries.
Disable introspection outside development unless your public API is meant to be discoverable.
Step 08 — Clients

Frontend Clients

Any HTTP client works: GraphQL is just JSON over POST /graphql. Use a library (Apollo Client, URQL) for caching and subscriptions, or plain fetch when you only need a couple of queries.

Plain fetch js
// Variables travel with the query

const response = await fetch('/graphql', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
  },
  body: JSON.stringify({
    query: `
      query Post($id: ID!) {
        post(id: $id) {
          title
          author { name }
        }
      }
    `,
    variables: { id: 1 },
  }),
});

const { data } = await response.json();
console.log(data.post);
curl bash
curl -X POST http://localhost:8000/graphql \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -d '{"query":"{ me { id name } }"}'
Lighthouse can also hand you a typed client. Run php artisan lighthouse:ide-helper to generate a .graphql file or TypeScript schema for Apollo / URQL with full autocompletion.
Step 09 — Testing

Testing the GraphQL API

Lighthouse ships a graphQL() test helper. Add the trait to your base TestCase, then write feature tests that run real queries against the schema.

tests/TestCase.php php
namespace Tests;

use Illuminate\Foundation\Testing\TestCase as BaseTestCase;
use Nuwave\Lighthouse\Testing\MakesGraphQLRequests;

abstract class TestCase extends BaseTestCase
{
    use MakesGraphQLRequests;
}
Feature Test — queries & errors php
namespace Tests\Feature\GraphQL;

use App\Models\Post;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class PostQueryTest extends TestCase
{
    use RefreshDatabase;

    public function test_posts_are_paginated(): void
    {
        Post::factory()->count(3)->create();

        $this->graphQL(/** @lang GraphQL */ '
            query {
                posts(first: 3) {
                    data { id title }
                }
            }
        ')->assertOk()
            ->assertJsonCount(3, 'data.posts.data');
    }

    public function test_mutation_requires_auth(): void
    {
        $this->graphQL(/** @lang GraphQL */ '
            mutation {
                createPost(input: { title: "Hi", body: "Hi", author_id: 1 }) {
                    id
                }
            }
        ')->assertGraphQLError();
    }
}
Test the contract, not the SQL. Queries against the real schema catch wrong field names, nullability mistakes, and auth gaps before your clients do.
